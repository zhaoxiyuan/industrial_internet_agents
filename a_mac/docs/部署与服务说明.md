# a 子项目功能与部署说明

本文以当前 `a/` 目录的代码和 `a/deploy/` 编排文件为准。命令中的密钥、域名和账号 ID 都是占位符；实际值放在 `a/.env` 和本机配置中，不要提交到仓库。

## 第一章 功能说明

本项目实现作业场景从监测、风险研判到处置和关闭的闭环：

1. **P6 监测**：`A5` 采集模拟 CV、传感器和定位数据，P6 识别异常、保存作业事件并调度后续处理。P6 的页面和 API 由 `agents/p6_monitor_agent.py` 提供。
2. **P7 风险研判**：P6 调用 `A6_A7` 与 P7 Agent 对事件作风险评估；P7 页面和 API 仍在 `p6` 服务内，没有独立容器。
3. **P8 处置**：P8 Agent 生成处置建议并通过飞书发送消息、卡片。`P8P9` 状态机管理作业状态，卡片按钮及 Web 操作触发状态变更，作业数据写入 `a/data/jobs/`。
4. **P9 审核与关闭**：审核结果进入 P8P9 状态机；符合关闭条件时 P9 生成关闭说明并更新飞书卡片。
5. **飞书交互**：Channel Gateway 接收飞书 Webhook、保存入站事件，并提供 `/v1/*` 内部 API。`chat_reply` 轮询事件，调用模型生成回复，再通过 Gateway 发回飞书。卡片按钮由 Gateway 同步转给 `webui` 或 `p8p9`。
6. **配置页面**：`app_config` 配置 LLM/VL；`feishu_cfg` 管理飞书账号、Gateway 配置和用户/群映射。两个页面涉及密钥，须经 Nginx BasicAuth 访问。

简化链路：`飞书 → ngrok/公网 HTTPS → Nginx → Gateway → chat_reply 或卡片回调服务 → P8P9`。监测链路为 `A5 → P6/P7 → P8 → P8P9/P9 → 飞书`。

## 第二章 Docker 镜像、容器和网络

### 2.1 两套编排

| 编排文件 | 适用入口 | 容器数 | `chat_reply` |
|---|---|---:|---|
| `a/deploy/docker-compose.yml` | Linux，Nginx 80/443 + 本机 ngrok 18080 | 7 | 不在 Docker 中，宿主机运行 |
| `a/deploy/docker-compose.mac.yml` | macOS/ngrok 入口，仅映射本机 18080 | 8 | 使用 `a-p6:latest` 镜像运行 `a-chat-reply` |

两套文件都使用名为 `internal` 的 Compose bridge 网络，容器通过服务名解析彼此。实际 Docker 网络名随 Compose 项目名变化。不要同时启动两套编排：它们使用相同的 `container_name`。`a/gateway/compose.yaml` 是 Gateway 的**独立示例**，不是整套 P6–P9 编排，也不应与上述编排同时启动同一个 Gateway。

| 服务 / 容器 | 镜像及构建文件 | 功能、监听端口 | 网络和外部依赖 |
|---|---|---|---|
| `gateway` / `a-gateway` | `a-gateway:latest`；`a/gateway/Dockerfile` | Node.js Channel Gateway，8787；飞书 Webhook、卡片回调代理、`/v1/*` | `internal`；经 Nginx 接收入站请求，向飞书 OpenAPI 出站；macOS 编排另把 8787 绑定到宿主机 `127.0.0.1` |
| `p6` / `a-p6` | `a-p6:latest`；`Dockerfile.p6` | P6/P7、A5/A6 看板与 API，5002 | `internal`；调用模型 API、Gateway/其他内部服务，挂载 `a/data` 和 `a/A5/logs` |
| `p8p9` / `a-p8p9` | `a-p8p9:latest`；`Dockerfile.p8p9` | P8/P9 状态机、卡片业务回调，8089 | `internal`；挂载 `a/data`，通过内部地址供 `webui`/Gateway 调用 |
| `app_config` / `a-app-config` | `a-app-config:latest`；`Dockerfile.app_config` | LLM/VL 配置 UI，5000 | `internal`；写 `a/.env` 和 `a/agent_config`；从 Nginx 的 `/admin/config/` 访问 |
| `feishu_cfg` / `a-feishu-cfg` | `a-feishu-cfg:latest`；`Dockerfile.feishu_cfg` | 飞书配置 UI，5003 | `internal`；写 `a/.env`、`a/gateway/config` 等；从 `/admin/feishu-cfg/` 访问 |
| `webui` / `a-webui` | `a-webui:latest`；`Dockerfile.webui` | 飞书卡片回调及辅助接口，8080 | Linux 编排用 **host** 网络；macOS 编排用 `internal`，并设置 `A_WEBUI_HOST=0.0.0.0` |
| `nginx` / `a-nginx` | `nginx:1.27-alpine`，官方镜像 | HTTPS/入口代理与 BasicAuth | `internal`；Linux 映射 80、443 和本机 18080；macOS 仅映射 `127.0.0.1:18080` |
| `chat_reply` / `a-chat-reply` | macOS 编排复用 `a-p6:latest` | 无监听端口；轮询 Gateway，调用 P8 Agent 和模型后回复飞书 | macOS：`internal`，`GATEWAY_HOST=http://gateway:8787`；Linux 默认编排：宿主机 Python 进程，需从宿主机访问 Gateway 8787 |

`Dockerfile.base` 定义 Python 公共基础镜像 `a-deploy-base`，**不是 Compose 服务**；构建业务镜像前须先构建它。持久化目录主要是 `a/data`、`a/A5/logs`、`a/agent_config` 和 `a/gateway/config`。`docker compose down` 不会删除这些 bind mount 的宿主机文件。

当前 Python Dockerfile 会把构建时的 `a/.env` 复制进镜像。把这些镜像视为含密钥的私有资产，不要推送到公共镜像仓库；更换密钥后还要重建相应镜像。

### 2.2 网络地址要区分

- bridge 容器之间用 `http://gateway:8787`、`http://p8p9:8089`、`http://webui:8080`，不能把 `127.0.0.1` 当作另一个容器。
- 宿主机 `chat_reply` 用 `http://127.0.0.1:8787`；这要求 Gateway 在宿主机回环地址发布 8787。**Linux 原版 Compose 没有发布此端口**，见第三章的修正清单。
- ngrok Agent 在宿主机运行，转发到 `http://127.0.0.1:18080`；18080 只绑定回环地址，不直接对公网开放。公网 TLS 由 ngrok 提供。
- Linux 原版 `webui` 使用 host 网络，监听宿主机 8080；macOS 编排将其置于 bridge 网络，Gateway 可通过 `webui:8080` 调用。两种地址不可混用。

## 第三章 部署、启动与外围配置

### 3.1 准备环境和密钥

安装 Docker Engine + Compose 插件；本机运行 `chat_reply` 时还需 Python 3.12 与 `a/requirements.txt` 的依赖。执行命令的工作目录均为 `a/deploy`，以下用 `cd /path/to/project/a/deploy` 表示实际项目路径。

先准备 `a/.env`。可参考 `a/deploy/.env.example`，但应以当前代码的变量名为准：

```env
CG_API_KEY=替换成随机长密钥
CHANNEL_GATEWAY_API_KEY=与CG_API_KEY相同
GATEWAY_HOST=http://gateway:8787
FEISHU_ACCOUNT_ID=P8P9
FEISHU_GROUP_MAP='{"oc_群ID":{"name":"作业群","description":"处置群"}}'
FEISHU_USER_MAP='{"ou_用户ID":{"role":"作业负责人","name":"张三"}}'
A5_LLM_API_KEY=替换成模型服务密钥
A5_LLM_BASE_URL=https://模型服务的兼容API地址
A5_LLM_MODEL=模型名
A5_LLM_PROTOCOL=openai
```

`app_config` 保存的主模型配置使用 `A5_LLM_*`；旧的非空 `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`OPENAI_MODEL` 会优先于对应 `A5_LLM_*`。若配置了旧变量，注意保持同一模型。VL 功能另需在配置页填写 `A5_VL_*`。模型供应商的地址、模型名、密钥必须来自实际供应商；容器需能出站访问该 API。

飞书账户凭据可在 `feishu_cfg` 页面维护；它会把 `P8P9` 之类的 account ID 写入 `a/gateway/config/config.feishu.local.json`，并把相应 `FEISHU_<ACCOUNT>_APP_ID`、`APP_SECRET`、`VERIFICATION_TOKEN` 写入 `a/.env`。Gateway 配置中的 `server.host` 应为 `0.0.0.0`、`server.apiKey` 应引用已设置的 `CG_API_KEY` 或 `CHANNEL_GATEWAY_API_KEY`，`channels.feishu.enabled` 应为 `true`，账号 ID 必须与 Webhook 路径及 `FEISHU_ACCOUNT_ID` 一致。**仅修改文件不会让运行中的 Gateway 重新读取配置**，保存后重建/重启相关容器。

配置目录、数据目录应先创建；`a/.env` 必须在 `docker compose build` 前存在，因为若干 Dockerfile 会 `COPY .env`。不要把真实密钥写入示例文件、镜像仓库或文档。

### 3.2 飞书开放平台

1. 创建企业自建应用，启用机器人，取得 App ID、App Secret；在应用的事件与回调设置中选择**请求 URL/Webhook** 模式。Gateway 不提供飞书长连接模式。
2. 开通接收消息和发送消息所需的飞书应用权限，并订阅 `im.message.receive_v1`。使用交互卡片时配置卡片按钮回调；如启用用户目录查询、文件/图片发送等功能，再按实际调用的飞书 API 开通相应权限。申请后创建并发布应用版本，把机器人加入目标群，确保目标用户可使用该应用。
3. 在配置页或 `a/.env` 设置每个飞书账号的 App ID、App Secret、Verification Token。若飞书侧启用了 Encrypt Key，Gateway 端也须一致；若未启用，Gateway 配置不要引用空的 Encrypt Key。
4. 事件订阅 URL 使用 `https://<公网域名>/webhooks/feishu/P8P9`，其中 `P8P9` **必须等于** `config.feishu.local.json` 中 `channels.feishu.accounts` 的键。卡片按钮回调 URL 使用 `https://<公网域名>/feishu/card/callback`；若使用 Gateway 标准 `card.action.trigger` 入口，也须保证其后端 `webui` 可达。飞书控制台的 URL 校验通过后再发布版本。
5. 在 `FEISHU_GROUP_MAP` 中填真实 `oc_...` 群 ID，在 `FEISHU_USER_MAP` 中填真实 `ou_...` 用户 ID；配置页的监听功能可在收到测试消息后帮助确认这些 ID。

### 3.3 ngrok 与入口代理

ngrok 运行在宿主机，先在 ngrok 控制台取得 Agent Authtoken，配置后启动：

```bash
ngrok config add-authtoken '<你的 authtoken>'
ngrok http http://127.0.0.1:18080
```

将输出的 `https://...` 域名填到飞书事件与卡片回调 URL。若 ngrok 分配的域名变化，需同步更新飞书控制台。Linux 可参照 `a/deploy/ngrok/ngrok.yml.example` 与 `ngrok.service` 设置 systemd；其中二进制路径和 `User` 要按服务器实际情况调整。`a/deploy/nginx/conf.d/mac-ngrok.conf` 已保留 Webhook 原始路径并转发 `/feishu/card/callback`。管理页面路径为 `/admin/p6/`、`/admin/p7/`、`/admin/config/`、`/admin/feishu-cfg/`。

在启动 Nginx 前创建 BasicAuth 文件：

```bash
cd /path/to/project/a/deploy
htpasswd -B -c nginx/htpasswd admin
```

### 3.4 macOS/ngrok 编排：8 个容器

这套编排的 Gateway、webui、p8p9 均在 bridge 网络，`chat_reply` 也在容器中。`Dockerfile.base` 没有 Compose 构建服务，应手动先构建：

```bash
cd /path/to/project/a
docker build -f deploy/Dockerfile.base -t a-deploy-base .
cd deploy
docker compose -p industrial-agents-mac -f docker-compose.mac.yml config --quiet
docker compose -p industrial-agents-mac -f docker-compose.mac.yml up -d --build
docker compose -p industrial-agents-mac -f docker-compose.mac.yml ps
```

Apple Silicon 若遇到特定依赖没有 arm64 wheel，应按依赖支持情况使用兼容镜像平台或调整依赖。配置页修改 `.env` 后，`env_file` 注入到已运行容器的环境变量不会自动刷新；重建受影响服务。macOS 编排已为 Gateway 配置 `A_WEBUI_HOST=webui`、`A_P8P9_HOST=p8p9`，为 webui 配置 `A_P8P9_BASE_URL=http://p8p9:8089`。

### 3.5 Linux：7 个容器 + 宿主机 `chat_reply`

Linux 原版 `docker-compose.yml` 可以构建，但要让**飞书消息和卡片链路实际可用**，先完成这些配置修正：

1. 给 `gateway` 增加 `ports: ["127.0.0.1:8787:8787"]`，供宿主机 `chat_reply` 访问；增加环境变量 `A_P8P9_HOST=p8p9`、`A_P8P9_PORT=8089`。
2. 原版 Gateway 默认找容器内 `127.0.0.1:8080`。建议让 `webui` 与其他服务同在 `internal` bridge：删去 `network_mode: host`，加 `networks: [internal]`，设置 `A_WEBUI_HOST=0.0.0.0`、`A_P8P9_BASE_URL=http://p8p9:8089`；Gateway 设置 `A_WEBUI_HOST=webui`、`A_WEBUI_PORT=8080`。这使两种卡片回调路径都能访问业务端。
3. `nginx/conf.d/agent.conf` 中 `/webhooks/feishu/` 的 `proxy_pass http://gateway:8787/;` 会去掉 `/webhooks/feishu/` 前缀。改成**不带末尾斜杠**的 `proxy_pass http://gateway:8787;`。另增加 `location = /feishu/card/callback { proxy_pass http://gateway:8787; }`，可参照 `mac-ngrok.conf`。80/443 和 18080 的相应 server 块都要处理。
4. 若使用公网域名/443，修改 `agent.conf` 的 `server_name` 和证书路径，先申请证书并保证宿主机 `/etc/letsencrypt` 可读。原版 Compose 的 Nginx **即使只用 ngrok**，也会加载 443 配置和证书挂载；没有有效证书时不能直接启动。仅用 ngrok 时可按 `docker-compose.mac.yml` 的 Nginx 挂载方式改为 `mac-ngrok.conf`，并只映射本机 18080。

修正后执行：

```bash
cd /path/to/project/a
docker build -f deploy/Dockerfile.base -t a-deploy-base .
cd deploy
docker compose -f docker-compose.yml config --quiet
docker compose -f docker-compose.yml up -d --build
docker compose -f docker-compose.yml ps
```

在宿主机为 `chat_reply` 安装 Python 依赖，并给它使用宿主机可访问的 Gateway 地址：

```bash
cd /path/to/project/a
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
export GATEWAY_HOST=http://127.0.0.1:8787
python -m A7.adapters.chat_reply run --account-id P8P9 --initial-sequence -1 --interval 1
```

可用 `python aaaseverstart.py start chat_reply` 管理后台进程，但要确保管理器所用 Python 环境已安装依赖、其进程继承上述 `GATEWAY_HOST`。使用 systemd 时应由 systemd 启动**一个**前台 `python -m A7.adapters.chat_reply run ...` 进程，并设置 `WorkingDirectory`、`Environment=GATEWAY_HOST=http://127.0.0.1:8787` 和 `Restart=on-failure`；不要同时用 `aaaseverstart.py start` 再启动同一个 systemd 服务。

### 3.6 验证与常见故障

```bash
# 在 a/deploy；macOS 编排给命令加 -p industrial-agents-mac -f docker-compose.mac.yml
docker compose ps
docker compose logs --tail 100 gateway p6 p8p9 webui nginx
docker compose exec nginx wget -q -O- http://gateway:8787/healthz
docker compose exec nginx wget -q -O- http://p8p9:8089/api/health
curl -i http://127.0.0.1:18080/admin/p6/api/health
```

最后一条未带 BasicAuth 时应返回 **401**，说明管理入口受保护；带 `curl -u admin` 可检查实际页面。飞书端向 Bot 发测试消息，检查 Gateway 收到事件、`chat_reply` 回复；再点一次卡片按钮，查看 `gateway`、`webui`、`p8p9` 日志。URL 校验失败时，逐一确认公网域名、ngrok 进程、Nginx 路由、账号 ID、Verification Token 和 Encrypt Key。`CHANNEL_DISABLED` 通常说明 Gateway 没加载启用飞书的 `config.feishu.local.json`；`CHANNEL_ACCOUNT_NOT_FOUND` 通常是账号 ID 不一致。配置更改后用 `docker compose up -d --force-recreate <服务名>`，代码或依赖更改后用 `docker compose up -d --build <服务名>`。

日常管理时在对应编排文件的目录执行 `docker compose up -d <服务名>`、`docker compose restart <服务名>`、`docker compose logs -f <服务名>` 或 `docker compose down`。macOS 编排每条命令均需加 `-p industrial-agents-mac -f docker-compose.mac.yml`；Linux 默认编排可加 `-f docker-compose.yml` 明确目标文件。

相关源文件：`a/deploy/docker-compose.yml`、`a/deploy/docker-compose.mac.yml`、`a/deploy/nginx/conf.d/`、`a/gateway/config/config.feishu.local.json`、`a/aaaseverstart.py`。
