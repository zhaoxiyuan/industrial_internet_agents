# 工业 Agent 平台 Skill 标准与实施方案

> 版本：设计草案 v0.3；日期：2026-09-28。阅读顺序：目标与对象 → Skill 包标准 → Agent 和部署 → 对话、定时任务与上下文 → 管理界面 → 分期验收。`industrial.ai/v1alpha1` 是本平台拟定义的协议，不是 Agent Skills、OpenClaw 或 Kubernetes 的现有 API。本文未实施代码，另一平台源码仍待核查。

## 1. 目标与关键决定

平台应让管理员完成一条明确的配置链：**创建 Agent → 选择运行位置 → 安装一个或多个工业 Skill → 配置/部署各 Skill 声明的 Docker 依赖 → 将 Skill 实例绑定给 Agent → 接入对话或定时任务 → 查看实际运行结果**。一个 Agent 可以绑定一个 Skill，也可以绑定多个 Skill；同一 Skill 包也可供多个 Agent 使用。

采用三层交付标准：

1. **通用 Skill 内容层**：沿用 `SKILL.md` 及 scripts/references/assets，描述何时使用能力、操作流程和业务约束。
2. **工业 Skill 包层**：增加机器可读清单，声明工具契约、配置 Schema、业务前端、容器部署资料、依赖、节点约束及检查方法。
3. **平台运行对象层**：记录 Agent、运行目标、部署实例、配置版本、绑定关系、触发器和任务，不把某工厂的地址、密钥、定时计划写死在通用包里。

标准 Skill 至少需要 SKILL.md，元信息含 name/description；工具注册、前端、Docker 服务与调度不属于该标准自动提供的能力。本平台扩展应保持标准内容可独立阅读，同时允许其他 Agent 不理解扩展清单时仍使用其中的说明。[Agent Skills 规范](https://agentskills.io/specification)

OpenClaw 将工具、Skill 和插件分别用于可调用动作、操作说明及运行时扩展，并支持 Agent 专属 Skill 可见范围。本平台借鉴其组织方式，把工业服务部署和边缘位置进一步纳入自定义协议；不宣称能直接导入任意 OpenClaw 插件并运行。[OpenClaw 能力分类](https://docs.openclaw.ai/tools)、[Skill 配置](https://docs.openclaw.ai/tools/skills-config)

## 2. 对象模型：先回答“什么绑定什么”

| 对象 | 定义与必要字段 | 关系及生命周期 |
|---|---|---|
| SkillPackage | 名称、不可变版本、digest、标准内容、工业清单 | 一份包可安装为多个现场实例 |
| SkillInstance | packageRef、site、配置修订、deploymentProfile、服务地址、Secret 引用、健康状态 | 一次现场安装；可能包含业务容器和配置前端，也可能连接已有服务 |
| AgentDefinition | agentId、名称、职责、模型引用、框架、工具权限、会话/状态策略 | 逻辑 Agent；创建并不自动拥有任意 Skill |
| AgentDeployment | agentRef、executionTargetRef、资源、副本、运行版本、期望/实际状态 | 指定 Agent 在哪个中心/边缘环境运行；逻辑 Agent 与 Pod 不一一等同 |
| AgentSkillBinding | agentDeploymentRef、skillInstanceRef、启用状态、可用工具子集、配置覆盖、revision | 解决“哪个 Agent 加载哪个 Skill 的哪个现场实例” |
| ExecutionTarget | 集群/namespace 或受管主机、site、中心/边缘属性、节点选择器、平台架构、网络/存储能力 | 定义可部署目标；实际 node/Pod/host 写入观察状态 |
| Trigger | chat/schedule，targetAgentDeployment、绑定范围、执行身份、输入与结果投递 | 触发已经部署的 Agent；首版对话和定时必需，事件/API 预留 |
| Conversation | sessionId、owner、agentDeployment、threadId、标题、状态、创建/更新时间、上下文策略与统计 | 前端会话对象；首版与一个 LangGraph thread_id 一对一绑定 |
| ConversationMessage | sessionId、messageId、role、内容/附件引用、时间、runId、显示状态 | 页面历史记录与审计；与模型实际使用的上下文分开 |
| ContextSnapshot | sessionId、checkpoint 引用、摘要、压缩版本、token 统计及策略 | 当前可继续对话的模型状态；支持压缩、恢复与限额提示 |
| ScheduleState | scheduleId、版本、上次成功时间、游标、已处理事件 ID、可选摘要 | 定时任务跨次保留的业务状态；与单次运行 checkpoint 分离 |
| Run | runId、triggerId、agentDeployment、binding/version/config 快照、状态、结果、审计 | 一次执行；固定版本快照，支持暂停/恢复 |

主关系：`SkillPackage → 多个 SkillInstance`；`AgentDefinition → 多个 AgentDeployment`；`一个 AgentDeployment → 1..N 个 AgentSkillBinding → 各自的 SkillInstance`；`一个 SkillInstance → 可被多个 AgentSkillBinding 引用`；`Trigger → AgentDeployment → Run`；`一个 Conversation ↔ 一个 LangGraph thread_id → 多次 Run/消息`。允许 Agent 暂时以 0 个绑定创建，但进入业务就绪状态前至少有一个可用能力；并不强制每个 Agent 都有独占 Skill 或独占 Docker 服务。

例如“动火监测 Skill 0.1”可安装为 A 厂实例和 B 厂实例，各有独立作业数据、飞书账号和服务地址。A 厂助手绑定 A 厂实例；中心值班助手经授权可同时绑定两个实例。同名工具通过绑定别名区分，避免一句“启动监测”误选现场。

约束：同一部署下相同绑定别名唯一；同版本号不允许不同包内容；工具名称冲突以 `bindingAlias.toolName` 隔离；配置覆盖必须在包声明的作用域内。共享 SkillInstance 的全局参数不能因某个 Agent 修改而静默改变其他 Agent。

## 3. 工业 Skill 包格式（标准核心）

### 3.1 目录与清单

```text
industrial-workflow/
  SKILL.md                         # 标准说明
  skill-package.yaml               # 本平台扩展清单
  tools/catalog.yaml               # 工具名、schema、适配器和状态要求
  schemas/config.schema.json       # 配置字段与约束
  schemas/config.ui.json           # 表单布局提示（平台扩展，可选）
  schemas/requests/                # 各工具请求/响应 Schema
  references/                     # 操作规则、错误恢复、飞书说明
  scripts/                        # 可选受控客户端，不随导入自动执行
  deploy/                         # 可选 K8s/Helm/Compose 模板
  ui/                             # 可选前端静态包或页面声明
  checks/                         # 声明式检查/受信执行器检查资料
  examples/                       # 对话、定时任务、测试输入
```

生产包必须固定版本及内容摘要。声明引用的文件必须存在、位于包内且可校验。私密参数不进包；脚本和模板存在不意味着平台会自动执行。导入只解析和校验，部署与启用是独立操作。

### 3.2 扩展字段契约

| 字段组 | 要求 | 定义 |
|---|---|---|
| apiVersion/kind/metadata | 必填 | 清单协议版本、IndustrialSkillPackage、name/version/displayName |
| skill.entrypoint | 必填 | 标准 SKILL.md 相对路径 |
| compatibility | 必填 | 平台适配器协议版本、Agent 运行时能力；有容器时声明 OS/CPU 架构 |
| tools | 必填，可为空 | 工具目录文件、命名空间、HTTP/受控命令等执行方式 |
| configuration | 必填，可为空 | Schema、字段作用域、Secret 类型、默认值、应用与重启规则 |
| services | 必填，可为空 | 逐个声明外围 Docker 服务的镜像版本/摘要、位置、端口、健康检查、数据与共享规则；无外围服务时显式 `[]` |
| deployment.profiles | 存在服务依赖时必填 | external、local-docker、kubernetes、compose 等支持模式和对应部署资料；不能只有一段不受控 Docker 命令 |
| ui | 可选 | 自动表单或专用前端；路由、目标服务、鉴权和配置协议 |
| placement | 存在约束时必填 | 必须同现场/同节点/可远程、硬件和数据范围限制 |
| dependencies | 可为空 | 外部服务、Skill 版本、运行环境、模型/通道与网络依赖 |
| lifecycle | 必填 | 加载、排空、卸载、存储保留、配置失败和升级恢复策略 |
| checks | 必填 | 包检查、依赖检查、就绪检查；业务验收与只读检查分开 |

缺少必填项禁止发布为“可执行工业 Skill”；仍可按纯说明 Skill 导入。首版必须提供一份扩展清单 JSON Schema，由前端、后端和运行时使用同一版本校验。`apiVersion` 是协议版本，包 `version` 是能力版本，binding `revision` 是运行配置修订，三者不能混用。

### 3.3 工具契约

每个工具必须声明：原始工具名、描述、输入/输出 Schema、执行适配器、所需服务、超时、并发限制、读写性质、重试/幂等方式、状态上下文要求和业务权限。对长期操作，应返回 operationId 与状态查询方式，不能把“已受理”当作完成。

统一运行上下文由平台注入：tenant/site、actor、agentId、runId、bindingId/revision、requestId；会话另外注入 channel/account/conversation/eventId。job_id 等业务参数经 Schema 校验。模型不能任意填写认证身份、凭据引用、目标主机或 LangGraph tool_call_id。

错误至少区分参数错误、权限不足、依赖不可用、业务冲突、超时、执行失败及结果未知。写操作在超时后先按 requestId 查询，不盲目重发。Skill 可见性和执行权限分别控制；隐藏 Skill 后，旧上下文仍可能要求调用工具，执行层必须重新校验绑定状态。

### 3.3.1 MCP 工具执行协议（首选）

工业包通过 `spec.tools.catalog` 声明期望工具契约，通过 `spec.tools.mcp.serviceRef` 指向包内声明的 MCP 外围服务。平台安装现场实例时保存 MCP URL 和 Secret 引用；导入只读文件，不执行包内代码。启用和运行时由平台 MCP 客户端调用 `tools/list`，仅把名称与输入契约匹配且当前绑定获准的工具注册给 LangChain；实际调用经 `tools/call`。服务未公布或契约不兼容的工具分别标为不可用，不要求前端逐项注册。若仅部分工具可用，实例可显示部分可用；托管部署资格仍按镜像与服务验收独立判断。

MCP Server 是业务适配边界。现有 HTTP 服务可由受认证的 MCP 包装服务调用；复杂 P8 状态更新必须先在业务服务暴露稳定远程接口，并保持状态、幂等及权限语义。平台每次调用前重查绑定和权限，校验输入/输出，并记录运行审计。MCP URL 与凭据属于现场实例配置，不能由模型参数指定。`SKILL.md` 继续承担业务说明，MCP 不代替容器、位置、存储、配置和 Agent 绑定声明。

### 3.4 外围 Docker 依赖声明（必审项）

每个可执行 Skill 包必须显式声明外围服务集合；没有外围服务也要写 `services: []`。包中声明**运行要求和可支持的部署方式**，实例中记录**实际运行在哪个节点、使用什么镜像/地址和配置**。平台不能从 `SKILL.md` 的自然语言描述推测要启动哪些容器。

每个服务条目至少包括：

| 字段 | 应明确的内容 |
|---|---|
| `serviceId`、`purpose` | 唯一逻辑名及职责，例如 p6、p8p9、gateway；哪些工具依赖它 |
| `required`、`dependsOn` | 必需或可选、服务间启动/就绪顺序；依赖图不得有环 |
| `image` | 仓库、受支持的版本范围、**已验证的不可变 digest**、CPU 架构；生产实例以 digest 锁定，不能只写 `latest` |
| `contract` | HTTP/消息协议、能力版本、探测端点；镜像版本和业务接口版本分别声明 |
| `placement` | 需要同 Agent 节点、同现场、指定设备节点，或允许跨节点访问；是否需要 GPU/设备/存储 |
| `network` | 服务端口、仅内网还是受认证外部入口、DNS/TLS 要求、允许调用方范围 |
| `resources` | 最小/建议 CPU、内存、可选 GPU 与并发上限 |
| `storage` | 持久卷/目录、数据类型、备份责任、升级兼容和卸载保留策略 |
| `config`、`secrets` | 配置 Schema 字段到容器环境/文件/Secret 的映射，生效时是否重启 |
| `health` | 启动、就绪和业务能力检查；可选依赖故障时影响哪些工具 |
| `lifecycle`、`shareScope` | 谁启动/停止/升级、是否可多 Agent 共享、引用与在途任务如何计算 |
| `profiles` | local-docker、受管 Compose、K8s、external 的部署资料和支持矩阵 |

包版本与服务版本必须分别管理：`SkillPackage 0.1.0` 可以支持 `p6 1.2.x`、`p8p9 2.1.x`，但每个实例安装时要生成锁定记录，写明最终选中的镜像 digest、配置修订和工具契约版本。升级 Skill 时逐项对照兼容范围；仅升级某个外围容器也须重新检查它所承诺的工具契约和数据迁移。多架构镜像要从目标节点的架构解析并保存最终摘要，防止中心测试通过而边缘无法拉取。

位置默认分开记录 `agentTarget`、每个 `serviceTarget`、`modelTarget`。本地 PoC 可以三者都指向同一本地 Docker 节点；未来 K8s 适配时把相同的 `sameNode`、`sameSite`、`remoteAllowed` 约束映射到集群、namespace、调度与网络策略。`sameSite` 不等于必须同一台机器；只有直接使用摄像头/GPU/本地盘的组件才要求指定设备节点。

默认部署流程：先锁定包及镜像→检查目标节点架构/资源/端口/存储→按依赖图创建持久存储与服务→等待就绪和契约检查→加载 Agent 工具→开放触发。若任一步失败，记录已创建资源与所有权并恢复原可用版本；不能把半启动的服务显示为已启用。停用一个绑定仅取消该 Agent 的使用权，共享服务是否停止由实例引用数和在途任务决定。

本地节点阶段建议由平台后端的**受管 Docker 适配器**执行部署；Agent/Skill 脚本不直接持有 Docker socket 或执行任意 `docker run`。适配器接口先固定 `plan / apply / inspect / stop / rollback`，并输出与未来 K8s 适配器一致的实例状态。这样后续主要替换服务部署实现，而不用修改 Skill 工具契约、Agent 绑定和配置页面。

### 3.5 配置契约

每个字段必须说明类型、校验、是否敏感、默认值、作用域及生效方式：

- `instance`：整套现场服务共用，例如设备源、P6 监听设置、网关账号。
- `binding`：某 Agent 使用该实例的默认值，例如默认作业区域、输出语言；只能覆盖白名单字段。
- `run`：单次任务参数，例如 job_id、场景和监测时长，不保存成全局配置。

配置同时记录 desiredRevision 与 observedRevision。保存先校验，再应用，再探测；需要重启时显示影响的服务及在途任务。失败应保持旧可用配置或进入明确的阻塞状态。模型密钥、飞书密钥只通过 Secret 引用注入；前端显示引用和就绪状态，不回显密钥。

## 4. Agent 创建及可视化 Skill 绑定标准

创建 Agent 至少收集：名称/职责、模型配置引用、运行框架、会话隔离键、状态存储、工具权限、任务并发/超时、executionTargetRef。用户随后选择已安装 SkillInstance；若缺实例，跳转到安装流程，完成后再建立绑定。

Agent 创建时还需选择会话存储和默认上下文策略：最大上下文预算、自动压缩阈值、保留最近消息数、会话保留期。前端可在 Agent 详情页覆盖单会话策略，但不得超过平台配额。

绑定必须记录明确版本、实例、作用域、工具集合和配置快照。Agent 的有效工具集合为平台权限、Agent 权限和绑定权限的交集；定时任务可进一步收窄。P8 包应提供全部 8 个工具，具体 Agent 可以基于角色选用子集。

同一界面需要显示三个独立状态：**Agent 正在运行、Skill 实例服务已就绪、绑定已加载**。仅 Agent Pod Running 或界面开关为开启，均不能证明工具可用。

运行时加载步骤：解析配置→确认实例就绪→生成 Skill 元信息索引→注册工具→回报版本/revision。正文按任务加载。当前框架不能热更新时，创建新版本 Agent 实例并排空旧实例；不能只修改文件后假定缓存中的 Agent 已更新。

## 5. 运行位置与工业边缘约束标准

必须分别定义三个位置：**Agent 推理/编排位置、工具或业务服务执行位置、模型服务位置**。中心 Agent 可以通过受控接口调用现场 P6 服务；边缘 Agent 也可能调用中心模型。界面应同时展示位置和跨域连线，不能把“Agent 在边缘”理解为全部数据不出现场。

ExecutionTarget 声明 `type=kubernetes|managed-compose-host`、clusterRef/namespace 或 hostRef、siteId、tier=center|edge、nodeSelector/affinity、架构、资源、网络域和存储能力。模型位置通过 modelRef 单独记录。离线边缘未配本地模型时，不能声称支持离线 Agent 推理。

| 约束 | 标准处理 |
|---|---|
| 现场摄像头/传感器只在边缘可达 | 数据采集服务要求 sameSite；只在确实依赖本地设备时要求 sameNode |
| 中心查询边缘记录 | 声明允许远程调用和可输出的数据字段；在调用方实际网络测试 |
| x86/ARM、GPU或设备资源 | 调度前核验架构与资源；依赖镜像提供相应构建 |
| 指定边缘节点离线 | 显示不可用或排队；禁止未经配置自动迁移到其他工厂 |
| 跨节点故障转移 | 仅迁移到同允许范围且可访问原状态/设备的目标；用租约防止双活监测 |
| 中心与边缘断连 | 首版默认暂停新调度，保留已获授权的在途任务至租约/时限；离线调度列为独立增强能力 |

同一 K8s 集群通过节点标签、nodeSelector/affinity 等调度；多集群先选 cluster，再在集群内选节点。直接指定固定节点不是默认方式，维护/迁移应受约束调度管理。[Kubernetes 节点调度](https://kubernetes.io/docs/concepts/scheduling-eviction/assign-pod-node/)

AgentDeployment 和 SkillInstance 分别记录 placement。绑定校验两者的网络、权限、现场和数据策略是否兼容。K8s Pod 的 localhost 不是 Mac 宿主机；Compose 服务名也不是跨集群地址。

## 6. 对话与定时任务标准

OpenClaw 提供消息到 Agent 的路由及定时自动化，可借鉴“明确目标 Agent、会话及结果投递”的组织方式。本平台统一把两者转为 RunRequest，使用同一工具执行和审计链路。[OpenClaw 多 Agent 路由](https://docs.openclaw.ai/concepts/multi-agent)、[自动化](https://docs.openclaw.ai/automation/cron-jobs)

### 6.1 对话 ChatTrigger

必填：channel、accountRef、允许的用户/群范围、targetAgentDeployment、sessionPolicy、replyPolicy。会话键至少包含租户、Agent、通道账号和 conversation；job_id 是业务关联，不替代会话身份。群聊注明是否需要 @、是否接管普通文本；同一路由只能有一个主响应者。

消息处理：验证来源→去重→匹配 Agent→建立 Run→调用已启用 Skill→回复原会话→记录结果与 ACK。回复失败与业务执行失败分别记录，重试回复不能重新创建工单。暂停对话入口、停用某个 Skill、停止 Agent 是三个操作。

### 6.2 定时 ScheduleTrigger

必须定义：scheduleId、cron/一次性时间、IANA 时区、targetAgentDeployment、执行身份、所需绑定、任务输入、并发策略、错过执行策略、超时、重试上限、启停状态、结果投递位置。

执行模式分为 `agent-task`（提供目标与上下文，让 Agent 按 Skill 判断）和 `tool-workflow`（按固定工具步骤执行）。固定采集链路不必每次由模型重新规划。界面显示下次执行时间和自然语言描述；后台保留原始时区与计划。

上下文按第 6.5 节的三层模型管理。日常巡检推荐 `concurrency=forbid`、错过时 `skip` 或受限 `latestOnce`；历史补跑必须明确，防止边缘恢复后大量重复处置。

以 `(scheduleId, scheduledTime)` 生成调度幂等键，运行中写操作再用 requestId 幂等。每条计划只允许一个调度所有者，中心调度与边缘调度不能同时触发。暂停计划不自动取消已经执行的任务。

实现可用平台调度器或 Kubernetes CronJob 生成 RunRequest，不能二者同时为同一计划计时。K8s CronJob 不是恰好执行一次的保证，业务仍需幂等与重入设计；根据集群版本核对 timezone/concurrency 等支持。[Kubernetes CronJob](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/)

### 6.3 统一执行请求

RunRequest 必须包含 triggerType/triggerId、agentDeploymentRef、requestId、actor、input、业务关联、绑定快照、deadline、resultDestination。对话从真实用户身份授权，定时使用专用服务身份及预先配置的动作范围。聊天中提出新计划时先形成可查看的时间/任务/目标配置，由有权限用户提交后成为 ScheduleTrigger；Skill 加载不自动创建计划。

### 6.4 对话会话与上下文管理（首版必需）

前端 Agent 页面设置对话栏：左侧会话列表（标题、最后消息时间、所属 Agent、占用状态），右侧消息区和输入框；支持新建、切换、重命名、删除会话、查看上下文占用、手动压缩。会话中显示正在执行/等待人工/压缩中/失败状态，以及当前加载的 Skill 版本。新建会话创建新的 sessionId；首次运行前为其分配并持久化唯一 thread_id；后续该会话的每条消息都传同一 `configurable.thread_id`。切换会话即切换 thread_id，不复用上一个会话的模型状态。[LangChain 短期记忆](https://docs.langchain.com/oss/python/langchain/short-term-memory)

绑定键建议为 `(tenantId, agentDeploymentId, sessionId) → threadId`，由服务端生成不可猜测的 threadId；客户端只提交自己有权访问的 sessionId。数据库加唯一约束并在创建事务内落盘，禁止用户直接指定他人的 threadId。首版一个平台会话只关联一个 AgentDeployment 和一个 LangGraph thread_id；更换 Agent、模型运行框架或 checkpoint 后端时创建新会话或进行显式迁移，不悄悄把旧 thread_id 接到新 Agent 上。

对话场景需区分入口来源：Web 新会话由用户显式创建；飞书群/私聊按 `tenant + channel + account + conversation` 查找或创建会话，再关联 thread_id；不同群和账号不得合并。一个工单 job_id 可出现在多个会话中，job_id 不是 thread_id。定时运行不自动加入用户会话；其 runId/thread_id、跨次 ScheduleState 与对话会话分别管理。

LangGraph checkpointer 保存线程状态，可按 thread_id 恢复；生产运行使用持久后端，不能用进程内 MemorySaver 作为跨 Pod 或重启后的会话存储。平台另存会话元数据、页面消息、附件和操作审计，以支持列表、筛选、删除和权限管理。业务工单/P8P9 状态不随聊天会话删除而删除。[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)

“上下文占用”应定义为**下一次模型调用预计占用的 token / 当前模型允许的上下文窗口**，包括系统指令、激活的 Skill、会话摘要与消息、工具定义和预留输出；不是数据库中全部历史消息的字符数。优先用模型 tokenizer 或实际调用 usage 统计，无法精确计算时显示“估算”和更新时间。界面同时显示最近一次调用的实际输入/输出 token 与费用（如可得），避免把两种数值混用；模型切换后重算预算。

压缩策略：达到阈值时提示或自动运行摘要压缩；保留最近若干完整消息，将较早消息写成带版本的摘要，记录压缩前后 token、模型、时间和来源 checkpoint。手动“压缩上下文”只改变后续模型可见的状态，页面完整聊天记录与工具审计仍保留。压缩前不得有正在执行的 Run 或待恢复的工具调用；需保持 Human/AI/Tool 消息配对及未完成人工审批状态。失败保留原 checkpoint，成功才切换到新状态。LangChain 提供 `SummarizationMiddleware` 等机制；触发阈值和保留策略由平台配置，不能假设 `create_agent` 默认自动压缩。[LangChain 摘要压缩](https://docs.langchain.com/oss/python/langchain/short-term-memory#summarize-messages)

删除会话分两步：先软删除并停止新消息/定时任务绑定；确认无进行中 Run、等待审批或仍需恢复的任务后，按保留策略清理 checkpoint 与消息/附件。界面删除入口需预览影响，默认保留业务记录和审计。要实现“永久清除”，还需检查具体 checkpointer 后端的删除能力和备份保留策略；不能只删会话列表记录却留下可被恢复的旧 thread 状态。删除后重新开聊须创建全新 sessionId/threadId。

建议首版 API：`POST/GET /agents/{id}/sessions`、`GET/PATCH/DELETE /sessions/{id}`、`GET/POST /sessions/{id}/messages`、`GET /sessions/{id}/context`、`POST /sessions/{id}/compact`。发送消息带 requestId，按会话串行或显式队列化运行，防止同一 thread 同时写入造成上下文竞争；压缩、删除与发送互斥并返回异步 operationId。跨 Agent 会话迁移、分叉和共享会话列为后续功能。

### 6.5 定时任务的三层上下文与运行历史

定时任务不能仅用“延续或不延续会话”描述上下文。首版明确区分三层：

| 层次 | 保存内容 | 标识与生命周期 |
|---|---|---|
| 任务定义 | schedule、目标 Agent/Skill、指令、执行身份、上下文策略、结果投递 | scheduleId；随配置修订保存 |
| 单次运行 | 本次输入、工具调用、checkpoint、结果、错误及 token 用量 | runId + 独立 thread_id；按运行保留期保存 |
| 跨次业务状态 | 上次成功时间、采集游标、已处理事件 ID、必要的结构化摘要 | ScheduleState；带版本和更新者，跨运行保存 |

**默认每次触发建立新的 runId/thread_id。** 下一次只读取任务定义及显式允许的 ScheduleState；不能把所有历史运行消息继续塞入模型上下文。需要连续分析时，`carrySummary` 只带入筛选过的上次摘要。游标、去重键和处置状态优先用结构化字段。状态只在定义的成功阶段提交；失败或人工重跑不应意外推进游标。

前端“运行历史”显示计划时间、实际时间、输入快照、结果、上下文用量、摘要、状态变更与错误。“重跑”创建新 runId/thread_id，引用原输入快照；是否更新 ScheduleState 由显式策略决定。“从断点恢复”续接**原 runId 和 thread_id/checkpoint**，并核验原绑定版本、执行身份及外部写操作结果。两者需在界面分成不同按钮。旧 checkpoint 可按保留期清理，但不能连同仍需使用的 ScheduleState 删除。

建议补充 `GET /schedules/{id}/runs`、`GET /schedules/{id}/state`、`POST /runs/{id}/rerun`、`POST /runs/{id}/resume`。同计划并发运行要串行化 ScheduleState 的读改写；提交带 expectedRevision，冲突时重新判断，避免两个运行互相覆盖游标。

## 7. 配置前端与依赖 Docker 的联动标准

### 7.1 部署模式与所有权

| deploymentProfile | 含义 | 平台责任 |
|---|---|---|
| external | 连接已运行的业务系统，例如现有 a_mac Compose | 配置地址与凭据、探测版本/能力；不拥有其容器生命周期 |
| kubernetes | 用包中经过校验的模板或 Helm 资料部署依赖服务 | 创建/观察 Deployment、Service、存储、配置和入口，按所有权卸载 |
| compose | 在登记的受管 Docker 主机部署 Compose | 由受管执行器运行已固定版本的部署资料，回报容器和服务健康度 |

包可以只支持其中一种，首版 a_mac 优先 external；K8s 不会直接运行 Compose 文件。K8s 部署应使用明确维护的 K8s/Helm 资料，而非承诺任意 Compose 自动等价转换。Compose 执行器使用受控身份，不把 Docker socket 暴露给通用 Agent/Skill 脚本。

每个服务遵守第 3.4 节的必审声明。平台记录 ownership=`managed|external`、实际镜像 digest、所在节点和配置修订。共享实例用引用和在途任务共同判定是否可停止；卸载一个 Agent 的绑定不能关闭其他 Agent 仍使用的服务。首版本地节点功能的部署模式为 `local-docker`，与未来 `kubernetes` 共用同一服务契约。

### 7.2 业务前端标准

每个 Skill 可声明两种 UI：

- **schema-form**：平台按 configuration Schema 生成配置表单，适合地址、场景、模型、账号等参数。
- **service-page**：复用专用业务前端，如监测看板、P8 工单页。声明 serviceRef、path、用途、所需权限、健康依赖、是否支持 iframe、URL 前缀、WebSocket、配置 API 契约。

默认通过平台认证代理打开页面，路由包含 instanceId，后端由绑定解析目标，禁止用户任意传 URL。鉴权凭据不放 URL；iframe 不兼容时使用经过认证的独立页面。页面链接可打开不等于配置已同步。

配置必须选定一个事实来源：建议平台配置 API 为主，业务页面也通过同一 API 更新；对现有只会写本地 .env 的前端，先做配置适配器，建立读回、版本确认与冲突检测，再支持双向编辑。改造完成前明确谁是主写入者，另一侧只读或显示待同步，不能让平台和业务 UI 各维护一份互不一致的配置。

### 7.3 生命周期联动

```text
导入包 → 验证契约 → 创建现场实例 → 选择位置/部署模式
→ 依赖检查 → 配置表单/专用页面 → 应用配置
→ 服务启动或连接 → 能力检查通过 → 绑定 Agent
→ 执行器确认工具注册 → 开放对话/允许定时运行
```

启用按钮执行上述阶段并展示进度。required 服务不可用时绑定不能 Ready；可选前端失败可降级显示，但若任务本身依赖该页面则阻塞对应能力。分别展示“服务就绪、配置生效、工具就绪、通道就绪”。liveness 不应因外部服务暂时断开而触发整个 Agent 重启。[Kubernetes 探针](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)

停用绑定→停止接纳其新 Run/相关计划变为 blocked→在途排空或保留待恢复状态→取消工具授权。依赖容器停止与数据删除需要单独管理动作：external 不停止；managed 且无人引用、无在途任务、策略允许时才停止；持久工单和审计默认保留。紧急撤销立即禁止后续工具执行，已发出的外部操作不承诺能撤回。

6. a_mac 包当前以 Docker 外部接口为首选。executionTarget 指向现场服务位置；中心 Agent 通过 Pod 可达的认证地址连接。后续才增加受管 Compose/K8s profile。

## 9. 生命周期、依赖和一致性规则

包状态：Imported/Validated/Rejected；实例状态：Configuring/Deploying/Ready/Degraded/Error；绑定状态：Disabled/Loading/Enabled/Draining/Error。健康度单独展示，不用一个开关覆盖所有状态。

依赖检查至少覆盖：包/schema 文件完整性、工具适配器、Agent 框架能力、版本兼容、必需凭据、模型、飞书、实际执行位置的网络、节点架构、存储、同现场限制、服务健康、Skill 循环依赖、共享实例影响及配置修订。所有报告记录版本/配置摘要、检查位置、时间、有效期和可执行修复建议；检查不自动安装任意外部依赖。

多副本执行器必须确认 binding revision；未确认实例不接相关新任务。每次执行校验授权和租约，避免旧 Pod 在网络隔离后继续接受已撤销权限。以 requestId + 工具业务键防重复写；调度和消息入口使用各自事件幂等键。

升级先验证新包和配置/状态兼容，再切换新任务；在途任务固定旧版本。数据库和配置迁移必须声明可否回退，备份与恢复方法；回滚包不等于自动恢复已迁移数据库。未声明兼容的暂停任务不得直接换新版本继续。

包存储与运行数据分离，镜像/包固定 digest，Secret 只按执行身份可用范围挂载。K8s Secret 的 base64 不是加密，使用目标平台现有密钥保护与访问控制。[Kubernetes Secret](https://kubernetes.io/docs/concepts/configuration/secret/)

## 10. 依据标准梳理管理功能

| 页面/模块 | 必备功能 | 对应标准对象 |
|---|---|---|
| Agent 管理 | 创建、模型/职责、运行位置、启动/停止、实例状态与会话 | AgentDefinition/Deployment |
| 对话栏与会话管理 | 新建/切换/重命名/删除会话、消息历史、上下文占用、手动/自动压缩状态 | Conversation/Message/ContextSnapshot |
| Skill 仓库 | 导入、结构校验、版本/摘要、工具和依赖、升级比较 | SkillPackage |
| 现场实例管理 | 选择 external/K8s/Compose、配置、部署进度、服务状态和页面入口 | SkillInstance |
| Agent–Skill 矩阵 | 行为 Agent、列为实例；可视化启停，显示版本、场所、失败原因 | AgentSkillBinding |
| 运行拓扑 | 中心/边缘节点、Agent、业务服务、模型位置及连通状态 | ExecutionTarget/部署对象 |
| 对话接入 | Web/飞书账号、群/用户范围、路由 Agent、会话记录 | ChatTrigger |
| 定时任务 | 创建计划、时区、下次执行、目标 Agent/Skill、上下文策略、结果目标、暂停/补跑 | ScheduleTrigger/ScheduleState |
| 定时运行历史 | 每次运行的独立 thread、上下文用量、状态变更、重跑与断点恢复 | Run/ContextSnapshot/ScheduleState |
| 依赖诊断 | 逐项缺失/失败、实际执行节点探测、配置生效情况 | 检查报告 |
| 运行与审计 | 消息/计划→Run→工具→外部任务的关联、耗时、失败、人工恢复 | Run/Operation/Audit |
| 卸载/回滚 | 展示受影响 Agent/计划/共享服务，在途排空、版本与数据保留 | 绑定及实例生命周期 |

后端建议按包目录、实例部署、Agent 注册、绑定协调、触发调度、统一工具执行和配置代理划分模块，复用现有平台组件。所有变更通过 Operation 异步记录，以 desiredRevision/observedRevision 表示实际生效；前端可轮询或订阅进度。

管理接口至少包括：包导入/版本；Agent 创建/部署；ExecutionTarget 注册/探测；实例配置/部署/页面代理；绑定启停/升级；会话 CRUD/消息发送/上下文统计与压缩；对话路由；定时任务 CRUD/暂停/手动运行；运行历史、重跑、断点恢复和 ScheduleState 查询；依赖检查；Run/Operation 查询。写接口带 requestId 和 expectedRevision，禁止并发编辑覆盖。

## 11. 分期交付与验收

**第一期：本地节点 PoC 与协议冻结。** 先用一个轻量示例 Skill 验证 Agent 一对一和一对多绑定、服务版本/位置声明、`local-docker` 适配器部署、配置表单、工具注册、Web 对话栏、会话与 thread_id 绑定、上下文占用/压缩、定时任务的三层上下文与运行历史。再用 a_mac 的已有 Compose 服务测试 `external` 模式；位置选择须在实际 Docker 节点/适配器上核验。此期不要求完整 K8s 多节点调度。

**第二期：a_mac Skill 化与托管依赖。** 按根目录方案补齐 a_mac 工具、配置和飞书对话；把 P6、P8P9、Gateway 等各 Docker 服务逐项写进正式依赖清单，形成真实多容器实例。确认本地托管或现有 external 模式的启停、共享和数据保留，然后实现 K8s 部署适配。未支持的 profile 不可选。

**第三期：工业可靠性增强。** 多现场灰度、离线边缘调度、受控故障转移、多租户资源配额及完整数据迁移回滚。离线模式必须单独定义租约、授权过期、时钟和补发规则。

验收必须覆盖：

- 同一包在两个现场独立安装，两个 Agent 按绑定访问对应工单与配置，不串线。
- 一个 Agent 绑定一个 Skill 与多个 Skill 均可运行；多个 Agent 共用一个实例时，停用其中一个绑定不停止共享容器。
- 导入时若缺少外围服务版本、镜像摘要、位置/存储/健康信息则拒绝托管部署；在本地 Docker 节点按依赖顺序启动并显示每个服务的实际镜像与位置。
- 中心 Agent 和边缘 Agent 的实际运行节点可见；工具服务位置与模型位置正确显示。
- 启用时缺服务/配置/工具会阻塞并指出原因；全部就绪并获运行时确认后才能使用。
- 自然语言完成监测/查询/P8 操作；8 个 P8 工具逐项验证，查询返回真实状态。
- 飞书两轮对话上下文连续；定时任务在指定时区触发并向指定目标投递，重复消息/调度不重复执行业务动作。
- Web 新建两个会话得到不同 thread_id；分别连续对话可恢复，切换后不串上下文；重启 Agent 后会话仍可继续。
- 上下文占用能随消息/模型/Skill 变化而更新；达到阈值可压缩，页面历史仍完整；压缩失败保留旧状态，待审批期间不可误删上下文。
- 删除会话后旧 thread 不再可调用，清理按保留策略执行；工单、飞书卡片和审计仍可查询。
- 同一定时计划连续两次执行得到不同 runId/thread_id；仅按策略继承 ScheduleState，失败不推进游标；重跑创建新 thread，断点恢复续接原 thread；网页和飞书会话均不受影响。
- 配置页面修改能被版本化应用并读回；失败时保留旧版本或明确阻塞，不出现两份配置悄悄分叉。
- 停用绑定停止新调用/阻塞依赖计划，保留在途/待恢复记录；其他 Agent 的共享服务继续可用。
- 边缘节点离线不错误迁移到其他现场；升级失败可回退兼容版本，卸载不丢工单和审计。

进入实施前需核查另一项目的现有 Agent/Skill 注册 API、会话持久化、K8s 集群拓扑、边缘是否入集群、模型位置、受管 Docker 主机能力、统一认证/Secret 服务。本文定义目标契约，不能据此推定目标项目已有这些实现。

## 12. 参考与文档关系

### 当前落地进度（2026-09-28）

平台已提供目录/ZIP 包导入、逐项校验报告和内容快照。实际协议以 `schemas/skill-package.schema.json` 为准，工具与配置文件采用包内引用；静态检查不执行包代码。包必须携带 `package.lock.json`，其文件 SHA-256 与实际内容一致。原简化 JSON 演示记录停用，需重新导入完整包。

源包阶段允许 `image.verifiedDigest: null`，作为明确的“部署待完成”项；绝不把空摘要当作生产锁定版本。现场网络、健康、资源和 Secret 尚未验证时同样显示待完成。包结构合格允许导入，依赖未就绪禁止启用。`a_mac_skill` 是按此规则封装的源码包，镜像发布与 P8 门面实现完成后还需联调验收。

平台相关文件：`package_validation.py`（校验）、`package_store.py`（ZIP/不可变快照）及 `test_package_validation.py`（反例测试）。`a_mac_skill` 已作为独立 Skill 包保存，平台导入其他 Skill 不依赖特定业务包的生成脚本。平台尚未实现现场预检执行器，不能仅根据包作者声明认定服务已可用。
