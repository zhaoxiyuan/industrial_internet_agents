# 2026-09-09 更新记录

## 一、P1 人工审批合并

### 调整原因

P1 原来在 `permit_submit`、`jsa_analyze`、`permit_generate_draft` 和
`permit_check` 等工具执行前分别触发人工审批，导致一次 P1 出现多个确认窗口。

### 实际操作变化

- 移除 P1 逐工具审批。
- 保留阶段末的“作业票最终审批”。
- 系统先自动完成申请整理、JSA 安全分析和作业票草稿生成，再统一弹出一次审批窗口。
- 批准后进入 P2；否决后停止在 P1，并可从 P1 重新执行。
- P1 批准后，执行记录会从 `waiting` 正确更新为 `completed`。

## 二、删除 P1 完成提示窗口

- 删除“P1 阶段执行完成/即将进入 P2”的三秒倒计时小窗口。
- P1 完成状态继续显示在流程图和运行日志中。
- P1 的最终人工审批窗口不受影响。

## 三、修复连续审批窗口丢失

### 问题现象

批准当前阶段后，后端已经执行到下一个人工确认点，但页面没有弹出确认按钮；必须再次点击
“启动”并选择继续当前任务，确认窗口才出现。

### 原因

下一阶段进入 `waiting` 后，WebSocket 状态可能早于当前确认请求的 HTTP 响应到达。此时旧窗口
仍处于打开状态，前端会跳过新窗口；随后旧请求回调又关闭窗口，造成确认按钮丢失。

### 修复结果

- 提交批准或否决时，先关闭当前阶段窗口。
- 确认请求返回后不再无条件关闭窗口。
- 确认窗口记录所属阶段；下一阶段到达时会替换旧阶段窗口。
- 请求失败时，重新显示服务端最后推送的待确认阶段。
- 工作流抵达下一人工确认点后会自动弹窗，不再需要点击“启动”触发重连。

## 四、修复后续作业 WebSocket 消息丢失

### 问题现象

- 服务重启后的第一条作业通常可以完整运行。
- 后续作业的 P1 运行窗口偶发不显示。
- 工作流实际已经到 P2 `waiting`，但页面收不到确认窗口，重新连接后才出现。

### 原因与修复

原实现让每个 WebSocket 连接直接消费同一个全局队列。存在旧连接或多个连接时，它们会竞争
同一条消息；消息一旦被不匹配的连接取走，就会被丢弃。

- 状态和日志通道分别改为单一队列分发器。
- 分发器只消费一次消息，再按 `job_id` 扇出给该作业的所有连接。
- 客户端连接不再直接竞争全局队列，只负责接收广播和发送心跳。
- WebSocket 初始状态增加各阶段状态，重新连接时能同步当前执行位置。
- P1 工具日志绑定实际 `job_id`，不再使用 `*` 通配编号串入其他作业窗口。

## 五、删除 P1 运行窗口并补强恢复确认

- 完整删除“P1 作业许可执行中”窗口的 HTML、样式、日志检测和状态触发代码。
- P1 执行过程继续显示在流程图与日志区域，不再弹出运行小窗。
- 点击“启动 → 继续当前任务”恢复 P1 后，页面每 500ms 查询一次持久化工作流状态。
- 页面重载自动找回作业，或对已在运行的作业重新连接时，也会启动同样的状态查询。
- 一旦 P1 进入 `waiting`，立即显示最终审批窗口；WebSocket 推送丢失时也不需要再次点击启动。
- 查询到确认、完成或真实失败后停止轮询，页面重置也会取消旧轮询。

## 六、历史作业查看/继续与 P1 审批内容展示

### 左侧历史作业

- 左侧增加“新建作业 / 历史作业”切换入口，历史作业按作业编号倒序显示。
- 每条历史记录显示作业编号、作业内容、区域、申请人、当前阶段和状态。
- “查看”以只读方式加载该作业的流程状态与历史日志，不影响当前正在运行的作业。
- 历史记录操作拆分为“查看流程”和“查看作业单”。“查看作业单”会打开只读详情窗口，展示基本信息、人员资质、计划时间、关联许可、风险措施、气体检测和缺失项，不触发审批或恢复执行。
- 未完成作业显示“继续”：等待审批的作业直接恢复审批窗口，执行失败的作业从持久化检查点恢复。
- 已完成作业只允许查看，不显示“继续”，并避免旧的 P1 确认数据造成误判。

### P1 人工审批

- P1 最终审批窗口改为宽版作业票视图，不再只显示一句确认提示。
- 审批人可以核对作业编号、类型、等级、单位、区域、地点、设备/介质、作业内容、人员职责与资质、计划时间、关联许可证及附件。
- 风险与削减措施按对应关系展示；气体检测记录按时间、位置、氧气、LEL、有毒气体和结果展示。
- 待补充字段和校验问题集中提示；当数据明确标记为严重缺失时禁用批准按钮。
- 面向操作者的缺失项统一显示中文名称，例如“作业设备”“作业等级”“作业人员张三的资质证明”，不再暴露内部英文字段编码。
- 当模型未返回完整作业票结构时，根据本次申请内容和作业类型生成审批兜底内容，不再使用固定人员或设备示例。
- 测试用 mock 数据参照真实作业票结构补充，仍保留一键生成 mock 数据的测试能力。

### 后端只读接口

- 增加 `/api/workflow/history`，用于读取历史作业摘要。
- 增加 `/api/workflow/job-detail`，用于读取历史详情和 P1 审批所需的完整作业票数据。
- 作业编号限制为 17 位数字，历史读取不会修改或恢复工作流。

### 新建作业的数据来源分流

- “新建作业”增加“Mock 测试数据”和“真实作业许可”两个明确入口，操作者先选择数据来源再启动。
- Mock 模式继续使用内置示例，并可点击“更换一条 Mock 数据”，不受真实文件上传影响。
- 真实许可模式支持上传最大 10MB 的 `.docx` 文件，解析后将识别结果回填到作业申请区域供操作者核对和补录。
- 当前支持从作业许可表格识别许可类型、单位、地点、作业内容、人员、计划时间、关联许可和已勾选安全措施。
- 对空白模板不生成虚假业务数据；页面明确显示这是空白许可，并列出作业内容、地点、人员和时间等缺失项。
- 真实许可的关键字段没有补齐时不允许启动。补录完成后，启动的作业会标记数据来源为 DOCX，并保留源文件名称和许可类型信息。
- 已用用户提供的空白《动火作业许可证》验证，可识别模板类型并正确判定为空白。
