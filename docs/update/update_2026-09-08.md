# 更新日志 - 2026-09-08

## 概述

本次更新为工业互联网边缘智能作业监测系统添加了**执行状态管理**和**失败恢复机制**，增强了工作流的可靠性和可维护性。

## 一、新增文件

### 1. `agents/workflow/execution_status.py`

执行状态管理模块，负责记录每个阶段的执行次数、状态和历史，支持失败恢复。

#### 核心功能

| 函数 | 说明 |
|------|------|
| `classify_error(error_message)` | 根据错误信息分类错误类型 |
| `init_execution_status(job_id)` | 初始化执行状态 |
| `get_execution_status(job_id)` | 获取执行状态 |
| `update_stage_status(job_id, stage, status, error, duration_ms)` | 更新阶段状态 |
| `can_retry_stage(job_id, stage)` | 检查阶段是否可以重试 |
| `get_retry_delay(attempt)` | 获取重试延迟（指数退避） |
| `get_failed_stage(job_id)` | 获取第一个失败的阶段 |
| `is_stage_critical(stage)` | 检查阶段是否是关键阶段 |

#### 错误分类

```python
ERROR_TYPES = {
    "temporary": [  # 临时性错误，可自动重试
        "timeout", "rate_limit", "rate limit",
        "network_error", "network error",
        "5xx_error", "connection_refused",
        "LLM rate limit", "overloaded",
        "temporarily unavailable",
    ],
    "business": [  # 业务逻辑错误，需人工介入
        "invalid_parameter", "invalid parameter",
        "data_format_error", "data format error",
        "permission_denied", "permission denied",
        "not_found", "not found",
        "validation_error", "validation error",
    ],
    "config": [  # 配置错误，需修复配置
        "model_not_found", "api_key_invalid",
        "missing_config", "Unable to infer model",
        "CONFIG_ENV_MISSING",
    ],
}
```

#### 阶段配置

```python

    "P3":  {"critical": True,  "max_attempts": 3, "retry_on_temporary": True},
    "P4":  {"critical": True,  "max_attempts": 2, "retry_on_temporary": True},
```

### 2. `agents/main_agent.py`

#### 新增函数：`execute_stage_with_retry()`

带重试机制的阶段执行函数：

```python
def execute_stage_with_retry(
    job_id: str, stage_name: str, executor, stage_config: dict,
    force: bool = False, continuation: bool = False
) -> dict
```

**功能**：
- 记录每个阶段的执行次数和历史
- 临时性错误自动重试（最多 3 次）
- 指数退避延迟（1s → 2s → 4s）
- HITL 暂停记录为 `waiting`，不计为执行失败
- 记录详细的执行日志

#### 重构函数：`run_workflow()`

**改进点**：
1. 初始化执行状态 (`init_execution_status`)
2. 使用 `execute_stage_with_retry()` 替代直接调用
3. 检查执行结果状态 (`result["completed"]`)
4. 根据阶段配置决定是否中断
5. 记录详细的失败日志

**关键逻辑**：

```python
# 检查阶段是否执行成功
if not result.get("completed"):
    error = result.get("error", "未知错误")
    error_type = classify_error(error)
    is_critical = is_stage_critical(stage_name)

    # 关键阶段失败，中断工作流
    if is_critical:
        return {"status": "error", ...}
    else:
        # 非关键阶段失败，记录日志，继续执行
        logger.warning(f"非关键阶段 {stage_name} 失败，继续执行")
```

### 3. `web/api/workflow.py`

#### 新增函数：`handle_workflow_resume()`

从失败阶段恢复执行的 API 处理函数。

恢复时保留原作业申请、执行次数和已完成阶段，不重新初始化工作流；`stage`
决定真正的执行起点。重复恢复同一正在执行的作业会返回 HTTP 409。

**请求体**：
```json

```

**响应**：

```json
    "job_id": "20260908093711563",
    "stage": "P2",
    "message": "从阶段 P2 恢复执行中..."
}
```

### 5. `agents/p1_permit_agent.py`

优化 P1 的人工确认执行链路：

- 首次执行只运行一个 HITL Agent，不再为了展示日志预先运行普通 Agent。
- 工具在用户确认前不会执行，日志由获批后的真实工具调用产生。
- 用户确认后使用 LangGraph `Command(resume=...)` 从原 checkpoint 继续。
- 不再删除 checkpoint，也不再创建 `P1-FRESH` Agent 从头重跑 P1。
- 同一次 P1 中连续出现多个工具确认时，仍记作同一次阶段执行，不增加重试次数。

实际操作上，P1 从“预执行一次 → 等待确认 → 整体重跑”改为“生成待审批操作 →
等待确认 → 从暂停位置继续”，减少模型调用时间并避免申请、JSA、作业票工具重复执行。

## 五、执行流程

### 正常流程

```
启动工作流
    │
    ▼
执行 P1 (attempt 1) ──成功──→ 执行 P2 (attempt 1) ──成功──→ ... ──成功──→ 完成
```

### 失败重试流程

```
执行 P1 (attempt 1) ──临时性错误──→ 等待 1s ──→ 执行 P1 (attempt 2) ──成功──→ 继续
```

### 失败中断流程

```
执行 P1 (attempt 1) ──业务错误──→ 记录日志 ──→ 中断工作流
                                                    │
                                                    ▼
                                          用户调用 /api/workflow/resume
                                                    │
                                                    ▼
                                          从 P1 恢复执行
```

### 非关键阶段失败流程

```
执行 P9 (attempt 1) ──失败──→ 记录日志 ──→ 继续执行 P10 ──→ ...
                              (P9 非关键，不中断)
```

## 七、设计决策

### 1. 为什么 P9、P10 不中断？

- **P9（闭环跟踪）**：闭环跟踪失败不应阻止作业完成，可以事后补录
- **P10（归档复盘）**：归档失败不影响作业本身，可以事后处理

### 2. 为什么使用指数退避？

- 避免在服务恢复前大量重试导致雪崩
- 给服务端足够的恢复时间
- 常见的重试策略，业界标准

### 3. 为什么区分错误类型？

- **临时性错误**：可能是网络波动、服务限流，重试可能成功
- **业务逻辑错误**：数据或逻辑问题，重试不会成功，需要人工介入
- **配置错误**：配置问题，需要修复配置后才能继续

## 八、后续优化建议

1. **持久化重试队列**：将重试任务持久化到数据库，支持跨进程重启

4. **手动跳过**：支持手动跳过失败阶段继续执行
5. **并行执行**：支持无依赖关系的阶段并行执行

## 九、P6 恢复问题修复

### 问题现象

- 作业 `20260908161833673` 执行到 P6 时失败
- 第 1 次执行记录的错误为：`'function' object has no attribute 'invoke'`

### 原因与修复

P6 中供主工作流调用的 LangChain 工具和 `/api/monitor/start` HTTP 接口都使用了
`monitor_start` 这个 Python 名称。后定义的 HTTP 接口覆盖了工作流工具，导致主工作流调用
`.invoke()` 时实际拿到普通异步函数。

现已将 HTTP 处理函数改为独立名称 `api_monitor_start`，URL 仍保持
`POST /api/monitor/start`，所以前端和接口调用方式不变。并增加回归测试，保证工作流工具仍可
`.invoke()`，同时 HTTP 路由仍然存在。

### 本次作业如何继续

1. 重启后端服务，使 P6 修复生效。
2. 在页面点击“继续执行”；或者调用：

```bash
curl -X POST http://localhost:8080/api/workflow/resume \
  -H "Content-Type: application/json" \
  -d '{"job_id": "20260908161833673", "stage": "P6"}'
```

恢复会从 P6 开始，已完成的 P1-P5 不会重跑。本次会记录为 P6 的第 2 次执行。

## 十、否决与页面恢复修复

### 否决不再继续后续阶段

- `approve`：完成当前确认并继续下一阶段。
- `reject`：立即停止工作流，将当前阶段记录为失败并写入“人工否决”原因；不会执行下一阶段。
- P1 被否决时会丢弃原 HITL checkpoint，避免后续重试错误地批准上一次被否决的工具调用。
- 点击“启动”并确认继续后，从被否决的阶段重新执行，形成新的 attempt。

### 刷新页面后保留断点作业

- 浏览器会保存当前未完成的作业编号、状态和阶段。
- 页面刷新或重新打开后，会向后端核对状态并自动重新连接原作业。
- 如果是更新前产生、尚未写入浏览器缓存的作业，页面会从后端找回最近一条未完成作业。
- 点击“启动”时优先恢复失败阶段，不再创建新作业。
- 恢复接口报错时保留原作业，不再询问并自动创建新作业；只有明确点击“重置”才清除当前作业。
