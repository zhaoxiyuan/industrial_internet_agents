# 风险处置卡片（P8/P9）交互设计与 job_status 维护方案

> 状态：设计草案。本文档面向 P8/P9 推送的风险卡片的多页交互改造，明确卡片 UI 状态机、`job_status` 状态机、回调路由、长记忆归档触发点。
>
> 本文档与现有 `P8_P9_UNIFIED_CLOSURE_AGENT_DESIGN_DRAFT.md` 互补：那份讲 P8/P9 业务逻辑，本份讲**卡片 UI 状态机、`job_status` 状态机、回调路由、长记忆归档触发点**，以及**P8 / P9 双智能体职责边界**（详见 §2.0.1）。
>
> **关键术语更正**：卡片绑定对象是 **P8 job_id**（不是单条 risk_event），一个 job 对应一张卡（1:1），但**并非每个 job 都会绑卡**——只有需要人介入的 job 才发卡片。详见 §2.0。

---

## 1. 设计目标与边界

### 1.1 目标

把 P8/P9 推送的风险处置卡片从**单页+多按钮**改造为**多页+状态机驱动**的卡片，对标飞书 cc connect 的体验：

| 维度 | 旧实现 | 新设计 |
|---|---|---|
| 卡片形态 | 单页 + 4 个 callback 按钮 | **多页 state-driven 卡片**，每个 `job_status` 一套 UI |
| 绑定关系 | 风险事件 → 卡片（1:N 错配） | **P8 job_id ↔ 卡片 1:1**（不是每 job 都绑） |
| 用户路径 | 群里点按钮 → 跳 Web → 群里看不到后续 | **群里卡片原地刷新**，状态可见、责任人可见、附件可见 |
| 防误触 | 群按钮任何人能点 | 文字确认 ≥ 10 字才 enable；"驳回"字样直接 disable；不限制操作人角色（**本期不引入鉴权**，详见 §7） |
| 长期记忆 | 关闭后由 P10 单独归档 | **`closed` 触发即归档**，P10 自动跟进 |
| 输入字段 | 走 Web 端表单 | **飞书卡片内嵌 input 表单** + Web 端可补完（双通道） |

### 1.2 边界

- 本设计**不改动** `p8_p9_closure_agent.py` 已有的工具签名（`acknowledge_disposition` / `submit_rectification_materials` / `record_closure_review` 等），仅在卡片渲染层 + Web 端落地。
- 不引入新依赖；卡片渲染沿用 `feishu_card_api.update_card_entity`（Cardkit 原位更新）+ `send_to_group_card`。
- Web 端详情页继续复用现有的 `closure/entry/<link_id>` 短时入口。

## 2. 卡片绑定模型与 6 态 × 6 模板

### 2.0 绑定模型（前置）

- **绑定对象**：飞书卡片绑定到 **P8 job_id**（不是单条 risk_event）。
- **基数**：**1:1** —— 一个 job 对应一张卡（`alert_id = job_id`）。
- **条件**：**并非每个 job 都绑卡**。绑卡与否是 **job 创建方**（外部触发者，可能是 P7、业务前端、运维配置等）的决策，**不由 P8/P9 agent 在运行时推断**。P8/P9 仅记录 `state["card_binding"]` 并遵循该决策：
  - 绑卡 → 走完整卡片生命周期（§2.4 六态）
  - 不绑卡 → `state["card_binding"] = null`，跳过所有 cardkit 调用；event 内部状态仍按 §3 推进，但不在飞书群渲染
- **绑定时机**：写入 job 初始 state 时一次性决定（在 `bind_card_to_job` 工具内记录，详见 §6.3）；后续不允许改动（避免飞书群里出现"幽灵卡"）。
- **不绑卡** 的常见场景（仅作示例，不构成强制规则，由 job 创建方按业务判断）：
  - 自动闭环场景（无需人介入）
  - 仅做归档/复盘用途（不进群）
  - 调用方配置上就不希望打扰群（如低风险演练、批量后处理）
- **绑卡** 的常见场景：
  - 跨多条 event、需要人协调处置
  - 单条但等级高或类型敏感
  - 调用方希望显式提示在群里

#### 2.0.1 P8 / P9 双智能体职责分工（前置）

**P8 与 P9 流程上串联在同一个 job 上，是两个不同职责的智能体**——两者**都需要 LLM 推理做决策**，所以才能称为"agent"。**纯流程性的卡片渲染与按钮路由是 service，不是 agent**（详见下方组件划分）。

##### 2.0.1.1 组件总览（4 类，2 agent + 2 service）

| 类别 | 组件 | 是否 agent | 需要 LLM 推理？ | 职责一句话 |
|---|---|---|---|---|
| **Agent** | **P8 处置 Agent** | ✅ | ✅ | 业务决策：人/agent 互动的"接取/上传/驳回/关闭"等动作该怎么做 |
| **Agent** | **P9 审核 Agent** | ✅ | ✅ | 材料质量审核：阅读 evidence + 复核文字，**给出"建议通过 / 建议驳回 + 理由"**，**无最终决定权** |
| Service | 卡片渲染 service | ❌ | ❌ | 纯流程：读 `job_status` → 选 §2.4 模板 → 调 Cardkit 原位更新 |
| Service | 回调路由 service | ❌ | ❌ | 纯流程：群按钮事件 → 校验合法性 → 路由到 P8 / P9 业务入口 |

> **关键澄清**：上一版设计把"P9 = 卡片动作 agent"是错的。**"读状态选模板渲染"是确定性流程，不需要 LLM；"按钮事件路由"是 if-else 表查询，也不需要 LLM**。把它们包装成 agent 既浪费推理成本，又模糊了"哪里需要 LLM 决策"的边界。本设计把它们降级为 service，P9 留给真正需要 LLM 决策的"材料审核"。

##### 2.0.1.2 P8 处置 Agent vs P9 审核 Agent

| 维度 | P8 处置 Agent（业务互动） | P9 审核 Agent（材料质量） |
|---|---|---|
| 决策对象 | "现在该做什么业务动作"（接取 / 上传 / 关闭 / 归档） | "这份材料够不够通过审核"（建议通过 / 建议驳回 + 置信度 + 理由） |
| 输入 | 人的意图（群按钮、输入框文字）+ 当前 job_status | 整改 evidence（附件元数据 + 复核文字）+ 原始 risk_event 上下文 |
| 输出 | 业务动作（调业务工具 + 写 job_status） | **仅给意见**：`{verdict: "pass" / "reject", confidence, per_event_rationale}`，**不写 job_status** |
| 权限 | **有状态写入权限**：调 `set_job_status(...)` 改 job_status | **无状态写入权限**：审核结果落到 `state["review"]["p9_opinion"]`，**必须由人（或人委托的 P8 路径）二次确认才会改 job_status** |
| 触发时机 | 群按钮触发 / Web 端提交触发 | `materials_in_audit` 进入时**异步**触发，不阻塞用户 |
| 错误处理 | 失败可重试，状态机保护 | 失败不阻断流程——超时或异常时**降级为 `waiting_human_review`**（让人工兜底） |

##### 2.0.1.3 关键约束（违反即视为 bug）

- **P9 不写状态**：P9 审核 agent 的输出**仅是意见**，不直接调 `set_job_status`；状态变更必须经"人审核通过"（群里点通过 + 输入理由）或"业务自动规则"（如置信度 > 0.95 且无高风险 event 才 auto-pass，但需在状态机表 §3.2 显式列出）。
- **P8 不审核材料**：P8 处置 agent **不调** P9 审核工具，也不自己"看一眼附件就判定通过"——避免自审自过。
- **service 不决策**：卡片渲染 service 只按模板渲染，不判断"该不该亮这个按钮"（按钮 enable 条件由 §2.4 模板里 if-else 表达，也不是 LLM 决策）；回调路由 service 只按路由表转交，不判断"这个 callback 合不合理"（合法性校验是 if-else，不是 LLM）。
- **唯一合法路径**：

```
群按钮事件
   └→ 回调路由 service（if-else 校验合法性）
        ├─ "接取 / 上传 / 关闭" 类 → 转 P8 业务工具入口
        └─ "AI 审核触发" 类（仅 Web 端或定时器触发）→ 调 P9 审核 agent
                                              ↓
                                          P9 给意见 → 写入 review 字段
                                              ↓
                                          状态机根据"意见 + 业务规则"决定
                                              ├─ auto-pass 高置信 → set_job_status(ready_to_close)
                                              └─ 其他 → set_job_status(waiting_human_review)
                                                  └→ 卡片渲染 service 渲染人工复核页
                                                       └→ 人在群里点"通过" → 路由 service 转 P8 → P8 写状态
```

##### 2.0.1.4 为什么 P8 / P9 必须分开（不是合一个 agent 更省事）

1. **决策类型不同**：P8 是"动作决策"（做什么），P9 是"质量判断"（材料够不够格）。两类决策的 prompt、工具集、上下文都不同，混在一起会让系统 prompt 同时塞业务规则 + 审核标准，互相干扰。
2. **权限分离**：P9 没有状态写入权，是防"AI 自审自过"的关键防线——审核 agent 不应该能把自己的"建议通过"直接变成"已通过"。
3. **异步可独立超时**：P9 审核可能跑 5-30 秒，必须异步不能阻塞；P8 业务互动通常是同步（用户点完按钮等结果）。两类 agent 的执行模型不一样，分开实现更清晰。
4. **可独立替换**：将来审核模型要换（比如换成更严的 prompt 或不同 LLM），只动 P9，不影响 P8 业务动作。
5. **审计清晰**：状态变更日志归 P8，审核意见日志归 P9，复盘"为什么这条通过了"时只需看 P9 意见 + 触发 auto-pass 的业务规则。

##### 2.0.1.5 service 与 agent 的边界（写代码时自检）

- 问"这个动作需不需要 LLM 推理？"——不需要 → service；需要 → agent。
- 搜索 `agents/p9_audit_agent.py` 代码：`grep -E "update_card_entity|send_event_card_for_web"` **应无命中**（P9 不渲染卡片，渲染是 service）。
- 搜索 service 代码（`services/card_render.py` / `services/callback_router.py`）：**不应 import langchain / 不应调用 LLM**——service 是纯 Python 流程函数。
- 搜索 `agents/p8_disposition_agent.py` 代码：`grep -E "agent_audit_job|review_materials"` **应无命中**（P8 不审材料，审核是 P9 的事）。
- 任何"P9 写状态"的提交都视为 bug——必须经状态机的二次确认路径（人或 auto-pass 规则）。

### 2.1 状态总览（job 级）

**关键约束速览**（详细见 §3.2 + §7）：

| 转换 | 谁能触发 | 校验 |
|---|---|---|
| `open → acknowledged` | **任意群里成员** | 状态机 + 乐观锁 + 抢锁 |
| `acknowledged → materials_in_audit`（含经过 `rectifying`） | **仅接取人本人** | 业务一致性（§7.2.1） |
| `materials_in_audit → waiting_human_review` / `ready_to_close` | agent 自动 | 异步审核 |
| `waiting_human_review → closed` | **任意群里成员**（允许接取人本人自审） | 文字 ≥ 10 字 + 不含"驳回" |
| `waiting_human_review → rectifying` | **任意群里成员** | 必须填驳回理由 |
| `ready_to_close → closed` | **任意群里成员** | 文字 ≥ 10 字 |
| **`acknowledged → open`**（退接） | **仅接取人本人**（业务一致性，§7.2.2） | 理由 ≥ 10 字 + 退接次数 < 2 |
| **`rectifying → open`**（退接） | **仅接取人本人**（业务一致性，§7.2.2） | 理由 ≥ 10 字 + 退接次数 < 2 |
| `closed` | （终态） | — |

### 2.2 卡片颜色规则（风险等级 + closed 态特例）

**核心规则**：
- **非 closed 态**：卡片标题区颜色由 `display_risk_level` 决定（等级越高越红）。
- **closed 态**：统一使用 `grey`（灰色），与 `display_risk_level` 无关。
- 状态用文本/badge 表示（待接取 / 已接取 / 已关闭 ...），不靠颜色传达。

> **为什么 closed 用灰色**：事件已闭环，警示意义结束；飞书群里滚动时，灰色卡片一眼可识别为"已处理"，避免与仍待处置的红/橙卡片混淆。如果需要复盘历史教训，去长期记忆/复盘系统查，不靠卡片颜色传递。

**多 event 的 job**：`display_risk_level = max(events[*].risk_level)`（取最严重的）。如果业务方有加权平均诉求，可改成 `sum` / 加权，但默认 max 最安全。

| 场景 | `display_risk_level` | 飞书 header template | 视觉感受 |
|---|---|---|---|
| `job_status != closed` | 0 | `grey` | 灰色 — 日常 |
| `job_status != closed` | 1 | `blue` | 蓝色 — 提醒 |
| `job_status != closed` | 2 | `orange` | 橙色 — 注意 |
| `job_status != closed` | 3 | `red` | 红色 — 警告 |
| `job_status != closed` | 4 | `red` | 红色 — 警示 |
| `job_status != closed` | 5 | `carmine` + 🚨 前缀 | 紧急 |
| `job_status == closed` | （任意） | `grey` | 灰色 — 已闭环 |

**特殊规则**：
- 危急（5 级）+ 任意**非 closed** 状态：标题前缀固定加 `🚨 `，背景色调到最深（`carmine`）。
- 较重（3-4 级）且 `job_status == open`：额外在 body 顶部加 1 行高亮提示「**高风险事件，请优先响应**」。
- **closed 卡片**：标题用 `grey`；body 的归档摘要区可用淡绿色块（`green` tag 装饰）表示"已归档"，但不覆盖标题色。
- 标题色由 `display_risk_level` + `job_status` 联合判定，公式化：`if job_status == closed: grey else: by risk_level`。

### 2.3 状态字段详细表（job 级）

| `job_status` | 中文名 | 触发条件 | 状态展示方式 | 主要操作 |
|---|---|---|---|---|
| `open` | 待接取 | P8 创建 job 并绑卡 | body badge：「⏳ 待接取」 | 群内**1** 个 primary 按钮：接取任务 |
| `acknowledged` | 已接取 | 群内点接取任务 | body badge：「✅ 已接取 · 张三」 | 显示接取人；附「提交材料」按钮 |
| `rectifying` | 整改中 | Web 端上传材料后回退 | body badge：「🔧 整改中」 | 等待上传；可继续追加 |
| `materials_in_audit` | agent 审核中 | 上传完材料 | body badge：「🤖 AI 审核中」 | 不可操作，等后台 |
| `waiting_human_review` | 人工复核 | agent 判定需人工 | body badge：「👁 等待复核」 | 复核文字 + 附件 + 跳转 + 输入栏 + 通过按钮 |
| `ready_to_close` | 待关闭确认 | 自动审核通过 | body badge：「✔ 准备关闭」 | 群内：链接查详情 + 输入栏 + ✅ 确认关闭按钮 |
| `closed` | 已关闭 | Web 端确认关闭 | body badge：「📦 已归档」 | 只读：归档摘要 + 附件列表 |

> 注：`pending_review` 是 P9 业务层的旧命名，本设计并入 `materials_in_audit` + `waiting_human_review`。迁移见 §6.2。

### 2.5 风险等级调整按钮（升级 / 降级）

> **设计动机**：现场情况瞬息万变，P7 在 A6 阶段给出的初始 `risk_level` 未必完全准确。**接取人在现场**可能发现：漏判了（要升级，比如发现更多违规者、传感器异常等）、或判重了（要降级，比如确认是误报、设备故障）。如果卡片只允许"接受原评级后走流程"，会出现两个问题：
> 1. **现场实际情况无法反馈**到风险等级——只能事后归档时复盘；
> 2. **接取人为了"省事"被动接受原评级**，错失现场最准确的信息源。
>
> 因此卡片必须有 **升级 / 降级** 两个按钮，让"现场判断"反哺回 risk_level，并写入审计日志。

#### 2.5.1 升级 / 降级适用状态

| job_status | 升级按钮 | 降级按钮 | 说明 |
|---|---|---|---|
| `open` | ❌ | ❌ | 未接取，无人有权调整 |
| `acknowledged` | ✅ | ❌ | 接取初期只允许上报风险（防过早降级） |
| `rectifying` | ✅ | ❌ | 整改中持续上报 |
| `materials_in_audit` | ✅ | ❌ | AI 审核期间仍可紧急升级（不等审核结果） |
| `waiting_human_review` | ✅ | ✅ | 复核人现场判断可升降 |
| `ready_to_close` | ✅ | ✅ | 关闭前最后调整机会 |
| `closed` | ❌ | ❌ | 已归档不可调整（要改需新开 job） |

#### 2.5.2 升级按钮规则（escalate_risk）

> **本期不做用户级鉴权**——允许任意群里成员触发升级（包括接取人本人）。质量保障通过"必填理由 + 强制 P7 重评 + 升级到 5 级紧急通知"实现，而非限制谁能点按钮。鉴权需求列入 §10 待开发 #7。

- **触发权限**：**任意群里成员**可触发（含接取人本人）；**不校验**用户角色。
- **必填字段**：
  - 新风险等级（int 1-5，必须 > 当前 `risk_level`，不允许"原地升级"）
  - 升级理由（≥ 10 字，建议 ≥ 30 字，强制中文 + 标点）
  - 可选：补充 evidence_id 列表（指向新发现的证据附件）
- **副作用**：
  - 写 `state["risk_changes"].append({action: "escalate", from, to, reason, evidence_ids, actor, at})`
  - 同步更新 event 级 `events[*].risk_level` + 重算 `display_risk_level`（§2.2）
  - **触发 P7 异步重评**（仅记录不阻塞；P7 的新评估落到 `state["p7_reassessments"]`，不覆盖现场判断）
  - **卡片立即原位刷新**（颜色变深 + 标题前缀更新）
  - 升级到 5 级时**额外触发紧急通知**：发单独告警到安全管理部门群 + 飞书 @ 班组长（不阻塞主流程，异步发）——这是流程动作，不是鉴权
- **不阻塞 job_status**：升级不改 `job_status`，只在原状态内调整 risk_level（避免打乱已有流程节点）。

#### 2.5.3 降级按钮规则（downgrade_risk）

> **本期不做用户级鉴权**——允许任意群里成员触发降级，**包括接取人本人**（不要求非同人）。防"自降级逃避"的措施改为**质量保障**而非**权限限制**：必须填 ≥ 20 字理由 + ≥ 1 个 evidence + P9 审核 agent 二次确认（异步）；任何环节不通过都不真正降级。鉴权需求列入 §10 待开发 #7。

- **触发权限**：**任意群里成员**可触发，**允许接取人本人发起降级**（不按角色/人区分）；**不校验**用户角色。
- **必填字段**：
  - 新风险等级（int 0-4，必须 < 当前 `risk_level`）
  - 降级理由（**≥ 20 字**，比升级更严；强制中文 + 标点）
  - **必须** 附加 ≥ 1 个 evidence_id（无新证据不允许降级，避免"凭空降级"）
- **副作用**：
  - **不直接改 risk_level**——先写 `state["risk_changes"].append({action: "downgrade_pending", from, to, reason, evidence_ids, actor, at})`
  - 触发 **P9 审核 agent 二次确认**（异步，质量保障而非鉴权）：
    - P9 阅读 evidence + 理由 + 原 risk_basis → 输出 `{agree_downgrade: bool, confidence, rationale}`
    - **P9 同意 + 业务规则通过**（如：降级后的等级仍 ≥ 当前 job 的最低等级阈值）→ 真正改 `risk_level` + 写 `state["risk_changes"]` 第二条（`action: "downgrade_approved"`）+ 触发卡片刷新
    - **P9 不同意** → 保持原 level，写 `state["risk_changes"]` 第二条（`action: "downgrade_rejected"` + P9 拒绝理由）+ 通知降级发起人"未通过，已记录"
  - **P9 超时 / 异常** → 降级视为失败，保持原 level；不阻塞 job_status 推进（用户可继续走原流程）
- **降级不等同关闭**：降级不影响 `job_status`，job 该走 materials_in_audit / waiting_human_review / closed 还是照走；只是 event.risk_level 变了。

#### 2.5.5 工具签名

```python

def escalate_risk(
    job_id: str,
    event_id: str,                  # 单 event 升级（不支持 job 级整体升级——避免掩盖个别 event 的真实变化）
    new_level: int,                 # 1-5，必须 > 当前
    reason: str,                    # ≥ 10 字
    evidence_ids: list[str] = [],   # 可选
    expected_version: int = 0,
    actor: dict = ...,              # {open_id, name, role}
) -> dict:
    """升级单条 event 的 risk_level，返回新 risk_level + change_record_id"""

@tool
def downgrade_risk(
    job_id: str,
    event_id: str,
    new_level: int,                 # 0-4，必须 < 当前
    reason: str,                    # ≥ 20 字
    evidence_ids: list[str],        # ≥ 1 个，必填
    expected_version: int = 0,
    actor: dict = ...,
) -> dict:
    """请求降级单条 event 的 risk_level（异步 P9 二次确认），返回 change_request_id"""
```

#### 2.5.6 字段扩展（在 §3.1 基础上增加）

| 字段 | 类型 | 位置 | 说明 |
|---|---|---|---|
| `risk_changes` | `[{action, from, to, reason, evidence_ids, actor, at, p9_verdict?}]` | state 顶层（job 级） | 升级/降级审计流水，每次动作追加一条；归档时全量写入长期记忆 |
| `p7_reassessments` | `[{trigger, new_risk_basis, at}]` | state 顶层（job 级） | P7 在升级后异步重评的历史（仅记录，不覆盖现场判断） |
| `risk_level` | int | event 级（已存在） | 单 event 风险等级，可被升级/降级修改 |

#### 2.5.7 状态机影响

**升级 / 降级不改变 `job_status`**——它们是**旁路审计动作**，在已有 job_status 状态机之外独立运行。状态机表 §3.2 的 LEGAL 转换不受影响。

但有一个**联动规则**：若升级导致 `display_risk_level` 跨阈值（如 2→3 进入"较重"），卡片自动追加 §2.2 的"**高风险事件，请优先响应**"提示行。

## 3. job_status 状态机详细定义

### 3.1 字段扩展（`A6_A7/service.py` 的 state store）

状态字段分两层：**job 级**（驱动卡片 UI）和 **event 级**（内部进度跟踪）。两者解耦：卡片只读 job 级，event 级独立推进。

**Job 级字段**（写在 `state["job"]` 或 state 顶层，对应一个 job_id）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `job_id` | str | ✅ | P8 job 唯一标识（卡片 alert_id） |
| `job_status` | enum | ✅ | `open` / `acknowledged` / `rectifying` / `materials_in_audit` / `waiting_human_review` / `ready_to_close` / `closed`（**驱动卡片 UI**） |
| `display_risk_level` | int (0-5) | ✅ | **卡片标题色由它决定**（详见 §2.2）；多 event 时 = `max(risk_level)` |
| `card_binding` | `{card_id, alert_id, chat_id, bound_at, bound_actor}` 或 null | ✅ | 是否已绑卡（详见 §2.0）；null = 未绑卡，不走卡片流程 |
| `accepted_by` | `{name, role, open_id, accepted_at}` | acknowledged 后必填 | 接取人信息（卡 §2.4.2 显示） |
| `materials.submissions` | `[{evidence_id, type, uri, uploaded_at, uploaded_by, event_ids[]}]` | 复用现有 + event_ids | 附件清单（每个附件可同时覆盖多条 event） |
| `materials.review_text` | str | ✅ 必填 | 接取人填写的整改自陈（卡 §2.4.4 显示，截断前 50 字，**中文字符+标点按 1 字算**）——**文字是必填项** |
| `review.ai_summary` | `{per_event: [{event_id, confidence, verdict}], aggregate_confidence, overall_verdict}` | ai_auditing 后 | AI 审核结果（job 级聚合 + per-event 明细） |
| `review.human_comment` | str | waiting_human_review 时必填 | 复核人意见（≥ 10 字） |
| `review.decided_by` | `{name, role, open_id, decided_at}` | approved/rejected 时 | 复核人信息 |
| `closed_at` | ISO ts | closed 时 | 关闭时间 |
| `archived_to_lt` | bool | closed 后**必须 = true**（不允许 false，没有"跳过归档"路径） | 是否已写入长期记忆；详见 §8 |
| `archived_at` | ISO ts | archived_to_lt=true 时 | 实际写入长期记忆的时间戳 |
| `archive_attempts` | int | 默认 0 | P10 归档失败重试次数（指数退避，最多 3 次） |
| `risk_changes` | `[{action, from, to, reason, evidence_ids, actor, at, p9_verdict?}]` | 每次升级/降级追加 | 风险等级变更审计流水；详见 §2.5 |
| `state_history` | `[{from, to, at, actor, reason}]` | 每次转换追加 | job_status 转换审计日志 |
| `version` | int | ✅ | 乐观锁 |

**Event 级字段**（写在 `state["events"][rid]`，内部进度跟踪，不直接驱动卡片）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `risk_event_id` | str | ✅ | 单条风险事件 id |
| `event_status` | enum | ✅ | `pending` / `disposing` / `disposed` / `failed`（与 job_status 同名空间但不同语义） |
| `risk_level` | int (0-5) | ✅ | 该 event 的风险等级 |
| `event_type` | str | ✅ | PPE 缺失 / 监护人离岗 等 |
| `involved_persons` | list | ✅ | 涉及人员 |
| `disposition.record` | `{submissions, status, ...}` | 复用现有 | event 级处置流水 |
| `review.record` | `{history, status, ...}` | 复用现有 | event 级复核流水 |
| `event_history` | list | 复用现有 | event 级审计日志 |

> **关键关系**：`job_status` 由 `events[*].event_status` 派生：
> - 任何 event 为 `pending` 或 `disposing` → `job_status` 不能进入 `closed`
> - 所有 event 为 `disposed` → `job_status` 可进入 `closed`
> - 推导在 `service._recompute_job_status(job_id)` 里集中执行，状态转换函数只接受 event 级变更
> - `display_risk_level` 由 `service._recompute_display_risk_level(job_id)` 派生：`max(events[*].risk_level)`；每次 event 的 `risk_level` 变化或 event 加入/移除时同步刷新；卡片标题色由它决定（详见 §2.2）

### 3.2 状态转换表（合法迁移，job 级）

| From | To | 触发方式 | 校验 |
|---|---|---|---|
| （无） | `open` | P8 创建 job 时（如绑卡则同时初始化 card_binding） | 必须有至少 1 条 source_event |
| `open` | `acknowledged` | 群 callback「接取任务」 | callback.operator 与 accepted_by.open_id 一致；version 校验；**记录 accepted_by.open_id + accepted_by.name**（后续业务一致性校验用） |
| `acknowledged` | `rectifying` | Web 端打开详情页（首次） | 仅作状态提示，可选 |
| `acknowledged` | `open` | 群 callback「退接」（接取人本人） | **业务一致性约束**：actor.open_id == state.accepted_by.open_id；reason ≥ 10 字；写 `state_history` 记录退接原因 |
| `rectifying` | `open` | 群 callback「退接」（接取人本人） | **业务一致性约束**：actor.open_id == state.accepted_by.open_id；reason ≥ 10 字；写 `state_history` 记录退接原因 |
| `rectifying` | `materials_in_audit` | Web 上传材料 | **`actor.open_id == state.accepted_by.open_id`**（业务一致性约束：接取人到上传材料只能同一人——非身份鉴权，详见 §7）；`review_text` 必填（文字必须有）+ `submissions` 可选（附件类型/数量灵活：照片/视频/文档/其他均可，0 个或多个都行） |
| `materials_in_audit` | `waiting_human_review` | agent 判定 `aggregate_confidence < 0.85` 或涉及高危 event | — |
| `materials_in_audit` | `ready_to_close` | agent 判定 `aggregate_confidence ≥ 0.85` 且无高危 event | — |
| `waiting_human_review` | `closed` | 群 callback「审核通过」+ 输入框文字 | 文字长度 ≥ 10 且不含「驳回」**本期不校验操作人角色**（详见 §7）；所有 event 派生为 `disposed` |
| `waiting_human_review` | `rectifying` | 群 callback「驳回」 | 必须填驳回理由；**本期不校验操作人角色**（详见 §7） |
| `ready_to_close` | `closed` | 群内 callback「确认关闭」+ 输入框文字 | 文字 ≥ 10 字；**本期不校验操作人角色**（允许接取人本人确认关闭，详见 §7）；所有 event 派生为 `disposed` |
| `closed` | （终态） | — | **不可回退**；**必须** 触发 P10 归档 hook → `archived_to_lt=true`（详见 §8）；不允许任何"跳过归档"的分支 |

### 3.3 非法转换防御

`service.py` 在每次 `set_job_status` 前调用 `_assert_transition(from, to)`：

```python
LEGAL = {
    None: {"open"},
    "open": {"acknowledged"},
    "acknowledged": {"rectifying"},
    "rectifying": {"materials_in_audit"},
    "materials_in_audit": {"waiting_human_review", "ready_to_close"},
    "waiting_human_review": {"closed", "rectifying"},
    "ready_to_close": {"closed"},
    "closed": set(),  # 终态
}
```

非法转换直接抛 `IllegalTransition`，卡片不动，前端返回错误 toast。

## 4. 关键交互流程

### 4.1 接取任务（群 callback → open → acknowledged）

```text
[责任人] 群里点击「接取任务」按钮
   ↓
飞书回调 → feishu_gateway_cli.feishu_card.process_card_callback
   ↓ action="acknowledge_disposition", value={job_id, expected_version}
A6_A7/adapters/chat_reply.py / 或 A7 closure agent 工具
   ↓
service.set_job_status(job_id, "acknowledged", {
    accepted_by: {name, role, open_id, accepted_at: now},
}, actor=operator, expected_version=...)
   ↓
state["version"]++
state["job_status_history"].append({from: open, to: acknowledged, ...})
   ↓
cards.build_job_card(state["job"], version=new_version, ...) → Card 2.0 dict
   ↓
update_job_card(job_id, version)  ← 内部 time.sleep(0.2) 防刷新冲突（详见 §5.6）
   ↓
feishu_card_api.update_card_entity(state["card_binding"]["card_id"], new_card, sequence=prev_seq+1)
   ↓
飞书原位刷新群里同一张卡（§2.4.2）
```

### 4.2 上传材料 + 复核文字（Web 端 → materials_in_audit）

```text
[责任人] 群里点「提交/补充材料」→ 跳 closure/entry/<link_id>
   ↓
Web 详情页（target=materials）：
   - 复核文字输入框（**必填**，至少 ≥ 1 字；建议 ≥ 20 字以提供有效上下文，但不硬限）
   - 附件上传（**可选**；类型灵活：照片/视频/文档/其他均可，0 个或多个都行；可勾选覆盖哪些 event）
   - 「提交」按钮
   ↓
Web POST → /api/closure/<link_id>/submit
   ↓
后台：submit_rectification_materials(job_id, evidence=[...], review_text=<必填>, event_ids=[...])
   ↓
service.set_job_status(job_id, "materials_in_audit", {materials: {submissions: [...], review_text: <非空>}})
   ↓
service.set_event_status(job_id, rid, "disposing", ...)  ← 每个被覆盖的 event 同步推进
   ↓
异步触发：agent_audit_job(job_id)  ← job 级，一次性审核 job 内所有 event
   ↓
原位刷新群里卡（§2.4.3）
```

要点：
- **文字必有，附件灵活**：必须填 `review_text`（给审核人/AI 看的整改说明）；附件 `submissions` 可传空数组或任意类型，不在代码里硬限"必须照片""必须视频"等。
- 校验逻辑：`if not materials.review_text.strip(): raise EmptyReviewText`，仅校验文字非空。
- 附件大小/类型/MIME 等走通用文件上传校验（OSS 服务端校验），不在本设计业务层硬编码。

### 4.3 agent 审核分流（job 级聚合）

```text
agent_audit_event(job_id) 完成，返回 per_event: [{event_id, confidence, verdict, ...}]
   ↓
aggregate_confidence = min(per_event[*].confidence)  ← 取最低，最保守
   ↓
has_high_risk_event = any(risk_level >= 3 for ev in events)
   ↓
if aggregate_confidence >= 0.85 AND NOT has_high_risk_event:
   → service.set_job_status(job_id, "ready_to_close", {review: {...}})
   → 卡片更新为 §2.4.5
else:
   → service.set_job_status(job_id, "waiting_human_review", {review: {...}})
   → 卡片更新为 §2.4.4（包含输入栏 + 通过按钮）
```

### 4.4 群内审核（waiting_human_review / ready_to_close → closed）

两条状态转换走同一回调流程，区别仅在 §4.3 的入口：

```text
[复核人] 在群里卡片输入框输入审核意见（≥ 10 字）
   ↓ 飞书客户端：input 元素实时校验，enable/disable 通过按钮
[复核人] 点击「✅ 审核通过」/「✅ 确认关闭」
   ↓
飞书回调 → process_card_callback
   ↓ action="approve_review", form_value.review_comment=<输入>, value={job_id, expected_version}
service.record_closure_review(
    job_id, decision="approved",
    comment=form_value.review_comment,
    decided_by={name, role, open_id, decided_at: now},
    expected_version=callback.expected_version,
)
   ↓ 内部：遍历 events，把每条 event 的 event_status 推为 disposed
service.set_job_status(job_id, "closed", {closed_at: now})
   ↓
异步触发：archive_job_to_long_term_memory(job_id)  ← P10 hook，一次性归档 job 内全部 event
   ↓
原位刷新群里卡（§2.4.6，archived_to_lt=true）
```

要点：
- **Web 链接只用来查详情，不承担动作**——跳 Web 不会触发状态变更；状态变更必须由群内 callback 发起。
- **本期不限制关闭动作的操作人**——允许接取人本人确认关闭（详见 §7 + §10 待开发 #7）；质量保障通过"文字 ≥ 10 字 + 含'驳回'直接 disable"实现，而非限制操作人角色。

### 4.5 驳回路径

```text
[复核人] 在群里卡片点击「驳回」（隐藏在二级菜单，避免误触）
   ↓
弹出 input：「驳回理由（≥ 20 字，必填）」
   ↓
service.record_closure_review(job_id, decision="rejected", comment=...)
   ↓
service.set_job_status(job_id, "rectifying", {materials: cleared})
   ↓ 内部：相关 event 的 event_status 回退到 disposing
卡片回到 §2.4.3（整改中）
```

### 4.6 退接路径（acknowledged / rectifying → open）

> **业务背景**：接取人发现自己接错了 / 工作冲突 / 临时离开，需要让 job 重新开放供他人接取。**不是身份鉴权**，是 job 内部的"主动放弃"语义——接取后到上传材料阶段必须同人（§7.2.1），想换人只能走"退接 → 重新接取"两步。

```text
[接取人] 在群里卡片（仅接取人本人可见「退接」按钮）点击「退接」
   ↓
弹出 input：「退接原因（≥ 10 字，必填）」
   ↓
service.relinquish_job(job_id, reason, expected_version, actor)
   ↓ 校验：actor.open_id == state.accepted_by.open_id（业务一致性约束，§7.2.2）
   ↓ 校验：state.relinquish_count[actor.open_id] < 2（防止频繁退接）
   ↓
service.set_job_status(job_id, "open", {accepted_by: 保留, relinquish_count: +1})
   ↓ 内部：state_history 追加退接记录（from / to / at / actor / reason）
   ↓
卡片立即原位刷新 → §2.4.1（open 态）「接取任务」按钮重新出现
   ↓
群内发简短提示：「{接取人姓名} 退接了该 job，原因：{退接原因}」
```

要点：
- **按钮可见性**：「退接」按钮只在 `acknowledged` / `rectifying` 态显示；只有 `accepted_by.open_id` 等于当前 callback 触发人时按钮 enable；其他人看到的按钮是 disabled 灰态（隐藏可见性可能更安全，但飞书回调需要按钮 token 预生成，所以用 disable 表达）。
- **accepted_by 字段保留**：退接后**不清空** `state.accepted_by`，保留审计可追溯"曾经谁接过"；job 回到 open 后新接取人会覆盖该字段。
- **重接许可**：job 回到 `open` 后**任意群里成员**可重新接取（包括原退接人本身，job 内一致性约束不限制"原接取人不能再接"——这是身份鉴权范畴，本期不做）。
- **次数限制**：同一接取人对同一 job 最多退接 2 次，第 3 次尝试 → service 返回错误「您已退接该 job 2 次，请确认是否继续处理」（业务规则，非鉴权）。
- **状态机影响**：状态转换表 §3.2 已显式列出 `acknowledged → open` 和 `rectifying → open` 两条 LEGAL 转换；§3.3 非法转换防御同步更新。

### 5.2 乐观锁（version）

每次 `set_job_status` / `set_event_status` 都必须传 `expected_version`：

```python
def set_job_status(self, job_id, new_status, *, actor, expected_version=None, **fields):
    state = self._load(job_id)
    if expected_version is not None and state["version"] != expected_version:
        raise VersionConflict(...)
    _assert_transition(state["job_status"], new_status)
    ...
    state["version"] += 1
    state["job_status"] = new_status
    state["job_status_history"].append({from: prev, to: new_status, at: now, actor, reason})
    self._atomic_save(state)
    return state["version"]

def set_event_status(self, job_id, rid, new_status, *, actor, expected_version=None, **fields):
    state = self._load(job_id)
    if expected_version is not None and state["version"] != expected_version:
        raise VersionConflict(...)
    ...
    state["version"] += 1
    state["events"][rid]["event_status"] = new_status
    self._atomic_save(state)
    self._recompute_job_status(job_id)  # 派生 job_status
    return state["version"]
```

飞书 callback 的 button value 自带 `expected_version`，与 service 的 version 对齐。

### 5.3 原子写

`services` 层沿用现有 `tempfile + os.replace` 模式（`A6_A7/adapters/personal_context.py:91` 已有同样模式可复用）。**禁止直接 `open(..., "w")`** —— 已踩过坑。

### 5.4 状态恢复（崩溃 / 重启）

启动时遍历 `state_store/*.json`，对 `job_status in {materials_in_audit, waiting_human_review}` 的 job：
- 若 `materials_in_audit` 时间戳距今 > 5 分钟 → 重启 `agent_audit_event(job_id)`（幂等：agent 内部按 `evidence_id` 去重）
- 若 `waiting_human_review` 时间戳距今 > 24 小时 → 触发升级通知（不在本设计范围）
- 未绑卡的 job（`card_binding is None`）跳过所有 UI 恢复逻辑，只恢复 event 级状态

### 5.5 审计追溯

`job_status_history` + `events[rid].event_history` 全程记录 `(from, to, at, actor, reason)`：
- 合规审计可回溯"谁在何时改了什么状态"
- 飞书回调的 `actor` 来自 callback payload 的 `operator.open_id`（防伪造）
- 异常状态（如 `materials_in_audit` 卡 5 分钟没动）由 `job_status_history` 时间戳定位
- 绑卡行为单独留痕：`card_binding.bound_at` + `bound_actor`

### 5.6 卡片刷新节流（0.2s 延迟）

**所有对已绑卡片的原位更新都必须 sleep 0.2s 后再调 `feishu_card_api.update_card_entity`**（与现有 `A6_A7/cards.py` / `feishu_sender.py` 的行为一致）。

**原因**（防止飞书卡片刷新冲突 bug）：
- 飞书 Cardkit 对同一张卡的连续 `update_card_entity` 调用如果间隔过短（< ~100ms），会出现 **sequence 错位** —— 后一次调用基于"旧 sequence"提交，被服务端拒绝，导致卡片停在旧版本、新内容丢失。
- 0.2s 是经验值：足够长让服务端消化上一次请求，又短到用户感知不到延迟。
- 在 callback 处理路径上尤其重要：用户点完按钮 → 状态变更 → 卡片刷新，可能在 50-100ms 内连续触发；不 sleep 会出现"按钮已点但卡片没更新"。

**实现要求**：
- 在 `cards.update_job_card(job_id, version)` 工具**入口处**统一 `time.sleep(0.2)`（不是每个调用方各自 sleep，便于集中调整）。
- 节流开关：若同一 job_id 在 0.2s 内已有 in-flight 的更新请求，**复用其结果**（merge + skip），避免并发打架。
- 日志：`update_card_entity` 调用前后打印 `card_id` + `sequence` + `latency_ms`，便于排查。

**仅作用于原位刷新**：第一次创建卡片（`bind_card_to_job` 内调 `create_card_entity`）不需要 sleep（无 sequence 概念）。

**未绑卡的 job**：`card_binding is None`，整个 §5.6 节逻辑自动跳过。

### 6.5 附件下载链接（短时有效）

**问题**：附件存于 OSS（Aliyun Object Storage 等），原始 OSS 签名 URL 暴露存储路径且较长；飞书 `link_button` 适合短 URL；**OSS 签名 URL 也会过期**——用户拿到卡片后隔几天再点附件可能失效。

**方案**：新增 `create_attachment_download_link` 工具，**中间层短时 token** + **实时换发 OSS 签名**。

#### 6.5.1 数据流

```
[Agent / Web 后端]                                              [用户]
    │                                                              │
    │ create_attachment_download_link(                              │
    │     evidence_id,                                             │
    │     expiry_minutes=60,                                       │
    │     actor=operator,                                          │
    │ )                                                            │
    │   ↓                                                          │
    │ link_store.create({                                          │
    │     token: <8-char random>,                                  │
    │     evidence_id: ...,                                        │
    │     expiry: now + 60min,                                     │
    │     actor: ...,                                              │
    │     consumed_count: 0,                                       │
    │ })                                                           │
    │   ↓                                                          │
    │ return "https://host/dl/<token>" + expiry_iso                 │
    │                                                              │
    └──────────────────────────────────────────────────────────────────→ Feishu card link_button
                                                                       │
                                                                       │ 用户点链接
                                                                       ▼
                                                [GET /dl/<token>]  Web endpoint
                                                    │
                                                    ├─ token 不存在 / 已过期 → 404 + 提示「链接已失效，请到群里刷新卡片」
                                                    ├─ 已超过 consume_count 上限 → 403
                                                    └─ 有效：
                                                         1. 校验 link 归属（飞书 open_id 与 actor 对齐；非用户角色鉴权，仅防 token 泄漏后被他人滥用——属于 §6.5 的 link 级校验，与 §7 的角色鉴权无关；后者本期不实现，详见 §10 待开发 #7）
                                                         2. 实时生成 OSS 签名 URL（短时 5 分钟有效）
                                                         3. 302 redirect → OSS
                                                         4. consume_count += 1
                                                         5. 异步记录审计日志
```

#### 6.5.2 工具签名

```python
def create_attachment_download_link(
    evidence_id: str,
    expiry_minutes: int = 24 * 60,      # 默认 1 天
    actor: {open_id, name, role} = ...,
    max_consume_count: int = 999,       # 单 token 最大下载次数（999 = 准无限）
) -> {
    "short_url": "https://host/dl/AbCdEf12",
    "expiry": "2026-09-16T11:35:00+08:00",
    "ttl_minutes": 1440,
    "max_consume_count": 999,
}
```

#### 6.5.3 与现有 `_links.create` 的关系

- `_links.create` 是**任务入口链接**（`closure/entry/<link_id>`），用户点进入 Web 工作台做交互操作；生命周期跟 job 走，过期 = job closed。
- `create_attachment_download_link` 是**附件下载链接**（`/dl/<token>`），用户点触发文件下载；生命周期是固定时长（默认 60 分钟），独立于 job 状态。

**两者并存，不合并**——入口链接走权限/会话，下载链接走短时 token，职责清晰。

#### 6.5.4 失效场景与处理

| 场景 | 表现 | 处理 |
|---|---|---|
| Token 未过期，OSS 签名 URL 过期 | 用户点了 `/dl/<token>` 但 302 后 OSS 返回 403 | Web 端捕获 → 重新生成 OSS 签名 → 再 302（用户无感） |
| Token 过期 | `/dl/<token>` 返回 404 | 提示「链接已失效（X 分钟前过期）」；引导用户回群点击重新刷新卡片（卡片持有者是原始责任人/审核人） |
| 长记忆归档后的回看 | 归档后卡片不再刷新，新用户想看附件 | （本设计阶段不涉及归档后回看；后续由其他模块负责） |
| 卡片原位刷新后旧 token 失效吗？ | **不失效** | 旧 token 独立有效，新 token 是新发的；多 token 共存没问题 |

#### 6.5.5 与卡片的关系

- `closed` 卡片的附件 link_button 的 `value.short_url` 在每次**原位刷新时**重新调 `create_attachment_download_link` 刷新（保持新鲜）
- 飞书对 link_button 的 `url` 长度有上限（~2048 字符），短 URL 完全够用
- 卡片里的"查看完整审核详情 →"是 `closure/entry/<link_id>`（任务入口链接），不走下载链接；两个 link 各管各的

#### 6.5.6 安全

- token 用 8 字符 base62 随机生成（足够熵）
- `/dl/<token>` 必须校验请求方 open_id（从飞书 webhook 上下文拿）与 `link.actor.open_id` 一致（防 token 外泄）
- 超过 `max_consume_count` 拒绝（防盗刷）
- 所有访问写审计日志：`(token, evidence_id, actor_open_id, ip, ua, ts)`

## 7. 防误触与业务一致性约束

> **核心区分**：本节包含**两类不同性质的保护**，需要清晰分开：
>
> | 类别 | 本期是否实现 | 说明 |
> |---|---|---|
> | **防误触机制**（input 校验 / 乐观锁 / 抢锁） | ✅ 做 | 流程性保护，与"谁能操作"无关 |
> | **业务一致性约束**（接取 → 上传材料同人；接取可退接） | ✅ 做 | job 内一致性规则，**不是**身份鉴权 |
> | **身份鉴权 / 角色权限映射**（"X 角色才能做 Y 操作"） | ❌ 不做 | 列为 §10 待开发 #7 |
>
> **重要澄清**：用户上次提到"不引入鉴权机制"指的是**身份鉴权**（"这个角色能不能做这个操作"），**不包含**业务一致性约束。业务一致性约束是 job 内部规则（"既然我接了，就得我自己做完；想退出得明确退接"），与身份无关。

### 7.1 防误触机制（流程性保护，保留）

| 场景 | 防护 |
|---|---|
| 复核通过误触 | 输入框 disable 按钮；文字 ≥ 10 字才 enable；输入「驳回」字样直接 disable（防"通过驳回"二义输入） |
| 重复点击同一按钮 | 飞书 callback 端 `expected_version` 与 state.version 校验，过期返回 409 |
| 长期记忆归档失败 | `archive_job_to_long_term_memory` 重试 3 次（指数退避）；仍失败 → 监控告警 + 后台持续重试到成功（详见 §8.3） |
| Web 端和群卡片并发 | 任何修改都走 `service.set_job_status` / `service.set_event_status`，乐观锁保证最终一致 |
| 多人同时接取同一个 job | callback 抢锁：先到先得；后到的返回 409 + toast「该 job 已被 XXX 接取」 |

### 7.2 业务一致性约束（job 内规则，本期实现）

> **与身份鉴权的区别**：身份鉴权问"这个人**有没有权限**做这事"（基于角色 / 人员白名单）；业务一致性约束问"这个动作在**这个 job 的流程里**是否由正确的人触发"（基于 job 自身记录的 accepted_by）。前者需要外部权限系统，后者只需要 state 里的一个字段。

#### 7.2.1 接取 → 上传材料同人约束

- **规则**：`acknowledged` / `rectifying` 状态下，**只有 `state.accepted_by.open_id` 记录的那个接取人**才能：
  - 在 Web 端 `submit_rectification_materials` 上传材料
  - 在群卡片点「退接」（详见 §7.2.2）
- **不限制**：群内其他成员仍可看到卡片 / 阅读附件 / 查看历史；只是不能上传材料和退接。
- **错误处理**：其他人尝试上传 → service 返回 403 + toast「该 job 已被 XXX 接取，请由接取人本人提交材料」+ 卡片不动。
- **实现位置**：`submit_rectification_materials` 工具入口处校验 `actor.open_id == state.accepted_by.open_id`（详见 §6.3.1）。
- **审计**：每次拦截记录到 `state_history`（不是错误，是流程约束）。
- **不延伸到下游**：`waiting_human_review` / `ready_to_close` / `closed` 阶段允许任意群里成员操作（按 §7.1 的"不限制"原则）——审核是跨角色协作，不应限制。

#### 7.2.2 退接（acknowledged / rectifying → open）

- **触发场景**：接取人发现自己接错了 / 工作冲突 / 临时离开 / 任务转交他人——可主动撤回接取，让 job 重新回到 `open` 状态供其他人接取。
- **触发方式**：群内卡片点「退接」按钮（仅接取人本人可见 + 可点）→ 弹出 input「退接原因（≥ 10 字）」 → 确认。
- **权限校验**：**业务一致性约束**——`actor.open_id == state.accepted_by.open_id`；**不是**身份鉴权（不查角色，只查 job 内接取人字段）。
- **状态转换**：`acknowledged → open` 或 `rectifying → open`（详见 §3.2 状态转换表）。
- **副作用**：
  - 写 `state_history.append({from: "acknowledged"/"rectifying", to: "open", at, actor, reason: <退接原因>})`
  - **不**清空 `state.accepted_by`（保留审计可追溯"曾经谁接过这个 job"）
  - 卡片立即原位刷新（恢复「接取任务」按钮 + 删除接取人信息）
  - 群内发一条简短提示：「XXX 退接了该 job，原因：{退接原因}」（不阻塞主流程）
- **次数限制**：**同一接取人**对**同一 job** 最多退接 2 次——第 3 次尝试时返回错误「您已退接该 job 2 次，请确认是否继续处理」（避免频繁退接造成流程反复）。该限制属于业务规则，不属于身份鉴权。
- **退接后重接**：job 回到 `open` 后，**任意群里成员**可重新接取（含原退接人，job 内一致性约束不限制"原接取人不能再接"）。

### 7.3 本期不实现的部分（明确清单）

## 8. 长记忆归档触发（与 P10 衔接）

> **铁律**：`job_status → closed` 后 **必须** 写入长期记忆，**没有"跳过归档"路径**。`archived_to_lt` 在 closed 状态下**只能**为 `true`，不允许为 `false` 永久存在。
>
> - 失败时：**重试到成功为止**（指数退避最多 3 次 → 仍失败则人工介入 + 监控告警），但 `archived_to_lt` 最终必须被置为 true。
> - 不存在"`closed` 但 `archived_to_lt=false` 长期滞留"的合法状态——要么还在重试中（`archive_attempts < 3`），要么已成功归档（`archived_to_lt=true`），要么进入**人工介入 + 监控告警**流程（仍持续重试）。
> - 任何代码路径都不允许"跳过 P10 归档"——包括但不限于：`closed → archived_to_lt=true` 的回写失败不能简单忽略；P10 agent 异常不能 silent fallback。

### 8.1 触发点

`job_status → closed` 的状态转换里加 hook（注意：是 **job 级**触发，不是 event 级）：

```python
def set_job_status(self, job_id, new_status, ...):
    ...
    if new_status == "closed":
        # job 级触发，一次性归档 job 内全部 event；MUST 路径，无跳过选项
        import threading
        threading.Thread(
            target=_archive_with_retry,
            args=(job_id,),
            daemon=True,
        ).start()
```

### 8.2 归档内容（按 job 聚合，必须全量写入）

- job 元数据（job_id / 涉及 event_ids / 关闭时间 / 接取人 / 审核人）
- 每条 event 的完整信息（risk_event_id / risk_level / first_seen / last_seen / event_history）
- **接取人填写的复核文字**（`materials.review_text`，全文**不截断**——卡片上虽截 50 字展示，归档必须完整）
- **审核人填写的审核意见**（`review.human_comment`，全文**不截断**）
- 完整 review（ai_summary 的 per_event 明细 + aggregate_confidence + overall_verdict）
- **风险等级变更流水**（`risk_changes` 全量，见 §2.5.6——含每次升级/降级的 from/to/reason/evidence_ids/actor/p9_verdict）
- 附件清单（manifest：type / uri / size / sha256；同一附件若覆盖多 event 只记一次）
- 处置链路 `job_status_history` + `events[*].event_history` 全量
- 接取人 + 审核人信息
- P7 重评流水（`p7_reassessments`，若有）

### 8.3 失败处理（必须重试到成功）

```python
def _archive_with_retry(self, job_id: str):
    """归档重试：指数退避，最多 3 次；任一成功即标记 archived_to_lt=true"""
    import time
    backoff = [60, 300, 900]  # 1min, 5min, 15min
    for attempt, wait in enumerate(backoff, start=1):
        try:
            archive_job_to_long_term_memory(job_id)  # P10 agent 实际写库
            self._set_field(job_id, "archived_to_lt", True)
            self._set_field(job_id, "archived_at", now_iso())
            self._set_field(job_id, "archive_attempts", attempt)
            return  # 成功
        except Exception as e:
            self._set_field(job_id, "archive_attempts", attempt)
            logger.exception(f"[archive] job={job_id} attempt={attempt} failed: {e}")
            if attempt == 3:
                # 第 3 次仍失败：人工介入 + 监控告警，但仍继续后台重试
                alert_oncall(f"[CRITICAL] job {job_id} 长期记忆归档 3 次失败，需人工处理")
                # 不返回，继续重试（间隔放大到 1 小时一次，直到成功）
                while True:
                    time.sleep(3600)
                    try:
                        archive_job_to_long_term_memory(job_id)
                        self._set_field(job_id, "archived_to_lt", True)
                        self._set_field(job_id, "archived_at", now_iso())
                        alert_oncall(f"[RESOLVED] job {job_id} 长期记忆归档最终成功")
                        return
                    except Exception:
                        alert_oncall(f"[CRITICAL] job {job_id} 长期记忆归档仍失败，继续重试")
            else:
                time.sleep(wait)
```

**关键不变量**：
- `archived_to_lt` **最终必须**为 true——不依赖"成功"分支，依赖持续重试 + 监控告警。
- **不允许**出现 `closed → archived_to_lt=false` 的永久终态。任何路径下产生的 `archived_to_lt=false` 都必须配合 `archive_attempts > 0` + 重试中 / 人工介入中。
- **数据完整性**：失败重试时**重新全量写入**——P10 archive agent 是幂等的（基于 job_id upsert），不需要担心重复写。
- **不丢失证据**：归档失败期间 `state["job"]` 全量保留（含 attachments + review_text + human_comment + risk_changes），不会因为归档失败而丢失现场信息；重试时基于 state 重新生成 archive payload。

### 8.4 与 P10 的衔接（不变）

- 写完后回写 `archived_to_lt=true` + `archived_at=<timestamp>`，P10 复盘阶段可按 job_id 查询。
- 归档成功不影响 job_status（仍为 `closed`）——长期记忆是 P10 独立服务，与卡片生命周期解耦。
- P10 提供 `GET /api/p10/jobs/{job_id}` 查询接口（不是优化项，是**必提供**——复盘依赖它）。
