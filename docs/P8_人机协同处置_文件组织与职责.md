## 3. `A7/prompt/` — 业务规则提示词（加载 / 修改 / 恢复默认）

> **设计原则**：业务规则的"出厂默认版"以 **Python 常量** 内嵌进 `.py`，避免依赖任何外部 `.md` 文件存在性；用户可调用函数 `save_rules()` **运行时覆盖**自定义版本（落到磁盘 `overrides/`），也可一键 `reset_rules()` 恢复默认。

### 3.1 目录结构

```
A7/prompt/
├── __init__.py
├── p8_prompt.py              # 唯一文件：默认常量 + 4 函数 + 单例 getter
└── overrides/                # 运行时生成（git 忽略）
    └── P8_RULES.user.md      # 业务用户通过 save_rules() 写入的自定义版
```

### 3.2 `A7/prompt/p8_prompt.py`（核心文件）

**职责**：

1. **默认版持久化** — 用 `P8_RULES_DEFAULT` 三引号常量作为 source of truth；不依赖任何 `.md` 文件存在性
2. **加载** — 优先读 `overrides/P8_RULES.user.md`，不存在则用默认常量
3. **修改** — 业务人员调用 `save_rules(content)` 写到 `overrides/`（不污染默认常量）
4. **恢复默认** — 调用 `reset_rules()` 删除 override 文件，下次加载自动回落到默认常量

**关键代码**：

```python
"""P8 业务规则提示词：加载 / 修改 / 恢复默认。

默认版内嵌为常量（source of truth）；
用户自定义版写到 overrides/ 目录；
加载优先级：overrides > 默认常量。
"""
import os
from pathlib import Path

# === 默认版（出厂；Git 跟踪；不依赖任何 .md 文件）=======================
P8_RULES_DEFAULT = """\
# P8 人机协同处置 业务规则

## 1. 风险叠加判定
当 P7 在同一作业 (job_id) 内输出多个 risk_event 时，按以下规则判定是否合并到同一 P8_job：
- 时间窗 ≤ 30 min 且同区域/同设备/同班组 → 必须合并
- 时间窗 ≤ 2 h 且风险描述指向同一根因 → 建议合并
- 时间窗 > 2 h 或无关联 → 不合并，各为独立 P8_job

合并后 max_level = 各事件 level 的 max；risk_basis 拼接所有事件的依据。
""".strip()  # ← 此处仅展示前 4 行；完整内容见主设计文档 § 5.3 / 仓库 git 历史

# === 路径常量 ===========================================================
PROMPT_DIR = Path(__file__).resolve().parent
OVERRIDES_DIR = PROMPT_DIR / "overrides"
DEFAULT_FILE_NAME = "P8_RULES.user.md"


def _override_path() -> Path:
    """override 文件路径：A7/prompt/overrides/P8_RULES.user.md"""
    return OVERRIDES_DIR / DEFAULT_FILE_NAME


# === 公开 API ============================================================

def load_rules() -> str:
    """加载当前生效的业务规则提示词。
    
    加载优先级：
        1. A7/prompt/overrides/P8_RULES.user.md  （用户自定义）
        2. P8_RULES_DEFAULT 常量                 （出厂默认）
    
    Returns:
        markdown 文本；trim 后的字符串
    """
    path = _override_path()
    if path.exists():
        return path.read_text(encoding="utf-8").strip()
    return P8_RULES_DEFAULT


def save_rules(content: str, *, ensure_ascii: bool = True) -> bool:
    """保存业务规则提示词到 override 文件。
    
    Args:
        content: 业务人员编辑后的完整 markdown 文本（覆盖式，不是增量）
        ensure_ascii: 写文件时是否使用 ensure_ascii（默认 True，跨平台兼容）
    
    Returns:
        True 成功；False 失败（异常被捕获并返回 False）
    
    Side effects:
        - 创建 A7/prompt/overrides/ 目录（如不存在）
        - 写入 A7/prompt/overrides/P8_RULES.user.md
        - 不修改 P8_RULES_DEFAULT 常量
    """
    try:
        OVERRIDES_DIR.mkdir(parents=True, exist_ok=True)
        path = _override_path()
        path.write_text(content, encoding="utf-8")
        return True
    except Exception:
        return False


def reset_rules() -> bool:
    """恢复默认：删除 override 文件，下次 load_rules() 自动回落到 P8_RULES_DEFAULT。
    
    Returns:
        True 成功（无论文件原本是否存在）；False 失败
    """
    try:
        path = _override_path()
        if path.exists():
            path.unlink()
        return True
    except Exception:
        return False


def get_default_rules() -> str:
    """返回出厂默认版常量（只读，不修改文件）。"""
    return P8_RULES_DEFAULT


def is_overridden() -> bool:
    """判断当前是否使用用户自定义版（override 文件是否存在）。"""
    return _override_path().exists()


# === 兼容旧名（与既有 P* 的 load_system_prompt 风格对齐；可选用）========
def load_rules_prompt(stage: str = "P8") -> str:
    """[DEPRECATED] 加载指定阶段的业务规则提示词。
    
    与 agents/utils/system_prompt.py 的 load_system_prompt() 风格对称；
    新代码请直接用 load_rules()，本函数仅作过渡期别名保留。
    """
    if stage != "P8":
        return ""
    return load_rules()
```

### 3.3 与 `agents/utils/system_prompt.py` 的边界

| 文件 | 加载内容 | 默认版来源 | 修改后行为 | 恢复默认 |
|------|---------|-----------|-----------|---------|
| `agents/utils/system_prompt.py` | `agents/system_prompt/{STAGE}_SYSTEM_PROMPT.md` | **磁盘 .md**（Git 跟踪） | 直接覆盖原 .md（**不可恢复**） | 从 Git 还原 |
| **`A7/prompt/p8_prompt.py`** | 业务规则（叠加 / 责任 / 通道） | **.py 内嵌常量** | 写 `overrides/*.user.md`（默认版不动） | `reset_rules()` 删 override |

- 业务规则（业务侧）— 改动频繁、不能依赖 Git → 必须有"非破坏性"的用户自定义层

```python
from enum import Enum
from pydantic import BaseModel, Field, field_validator
from typing import Literal

class P8JobStatus(str, Enum):
    PENDING = "pending"
    NOTIFIED = "notified"
    WAITING_DECISION = "waiting_decision"
    COMPLETED = "completed"
    REJECTED = "rejected"
    ESCALATED = "escalated"
    RESUMED = "resumed"

class RiskLevel(str, Enum):
    LOW = "LOW"
    MEDIUM = "MEDIUM"
    HIGH = "HIGH"
    CRITICAL = "CRITICAL"

class Channel(str, Enum):
    HITL = "HITL"
    PUSH = "PUSH"

class ActionType(str, Enum):
    APPROVE = "approve"
    REJECT = "reject"
    ESCALATE = "escalate"
    RECTIFY = "rectify"
    PAUSE = "pause"
    RESUME = "resume"

class P8Job(BaseModel):
    """工作记忆中的 P8_job（N:1，支持风险叠加）。"""
    p8_job_id: str = Field(..., pattern=r"^P8J-\d{8}-\d{6}-\d{3}$")
    a6_event_ids: list[str] = Field(..., min_length=1)
    risk_basis: str
    max_level: RiskLevel
    level_distribution: dict[RiskLevel, int] = {}
    urgency_emoji: str
    assignee_role: str
    status: P8JobStatus = P8JobStatus.PENDING
    channel: Channel | None = None
    decision: ActionType | None = None
    note: str = ""
    due_at: str  # ISO8601
    created_at: str  # ISO8601

    @field_validator("a6_event_ids")
    @classmethod
    def check_no_duplicates(cls, v):
        if len(v) != len(set(v)):
            raise ValueError("a6_event_ids must be unique within a P8_job")
        return v

class P8JobUpdate(BaseModel):
    """update_job 工具的入参模型。"""
    a6_event_ids: list[str] = Field(..., min_length=1)
    p8_job_id: str | None = None
    status: P8JobStatus | None = None
    channel: Channel | None = None
    note: str | None = None

class PushMessage(BaseModel):
    """飞书推送消息模板（单事件 / 聚合两版）。"""
    title: str
    body: str
    a6_event_ids: list[str]
    assignee_role: str
    risk_level: RiskLevel
    job_id: str  # 主流程作业 ID
    p8_job_id: str
    idempotency_key: str  # = p8_job_id
```

## 5. `A7/storage/` — 长期记忆后端（JSON 文件持久化）

### 5.0 为什么用 JSON 文件（不是 mock、不是 SQLite）

**当前方案**：把已归档 P8_job 写到磁盘上的 JSON 文件，进程重启数据仍在。

| 维度 | 当前（JSON 文件） | Mock（内存 dict） | SQLite / Redis |
|------|------------------|------------------|----------------|
| 进程重启后数据 | ✅ 保留 | ❌ 丢失 | ✅ 保留 |
| 实现复杂度 | **极低**（标准库 json） | 极低 | 中等（需 sqlite3 / redis 库） |
| 跨进程共享 | ✅ 文件系统级 | ❌ | ✅ |
| 容量 | 受磁盘限制 | 受进程内存限制 | 受磁盘/服务限制 |
| 适用阶段 | **Demo / MVP** | 临时调试 | 生产 / 大数据量 |

**为什么选 JSON 文件**：

1. **Demo 需要持久化**：之前 mock dict 在进程重启后丢失，不利于演示重现与跨会话查询
2. **零依赖**：标准库 `json` 即可，不需要 sqlite3 / redis-py
3. **可读可改**：开发期可以直接 `cat data/jobs/_long_term/p8_archive.json` 查看归档内容
4. **足够支撑当前场景**：归档数据量小（几百条），单文件 dump 性能不是瓶颈
5. **升级路径清晰**：未来若需要并发 / 大数据量，从 JSON 升级到 SQLite 时接口签名可保持兼容（`save_archived_job` / `get_archived_job` / ...）

### 5.1 存储路径与文件格式（双层结构）

P8 长期记忆采用**索引层 + 数据层**分离的双文件结构：

```
data/jobs/
├── _long_term/                       # 全局长期记忆目录（仓库级共享）
│   ├── p8_archive.index.json         # 索引层：p8_job_id → 一句话描述（轻量；LLM 每次 invoke 都看）
│   └── p8_archive.json               # 数据层：p8_job_id → 完整 archived P8Job（按需精确加载）
├── 20260810142245512/                # 单个主流程作业（job_id 子目录）
│   ├── p7_result.json
│   └── p8_result.json
└── ...
```

#### 5.1.1 为什么分两层

**问题**：LLM 调 `recall_jobs(query)` 时：

| 方案 | 优劣 |
|------|------|
| 单文件全量加载 | 简单但贵 — 100 条 P8_job × 500 字段 ≈ 5 万 token / 每次 invoke |
| 不分文件 | LLM 不知道"有哪些 P8_job 可查"，要么漏掉要么瞎猜 |
| **双层（推荐）** | **索引先扫（轻量）→ LLM 决策是否精确查（按需）** |

**好处**：

1. **省 token**：索引条目约 80 字 / 条；100 条 ≈ 8 KB；LLM 每次 invoke 看到的是"100 个 p8_job_id + 一句话"，而不是 100 个完整 JSON
2. **LLM 决策自主**：LLM 看到索引后自己判断"哪个相关，再去查详细"
3. **人类可读**：开发期可以直接 `cat p8_archive.index.json` 看长期记忆有啥

#### 5.1.2 索引层文件格式（`p8_archive.index.json`）

```json
{
  "P8J-20260813-180000-001": "[HIGH] 3 人同时段 PPE+噪声+受限区叠加；approve by zhang @ 2026-08-13 19:30",
  "P8J-20260813-190000-002": "[CRITICAL] 单一 event 罐区泄漏；escalate by HSE @ 2026-08-13 20:15",
  "P8J-20260814-090000-003": "[MEDIUM] 单 event 噪声超标；rectify by 班组长 @ 2026-08-14 10:00"
}
```

**索引条目生成**：复用 `A7/summary/p8_job_summarizer.py` 的 `summarize_p8_job()` 输出，再加 `[level]` 前缀与时间戳后缀。

格式模板：

```
[<max_level>] <risk_basis 截断 30 字>；<decision> by <decider> @ <archived_at 截 YYYY-MM-DD HH:MM>
```

#### 5.1.3 数据层文件格式（`p8_archive.json`）

```json
{
  "P8J-20260813-180000-001": {
    "p8_job_id": "P8J-20260813-180000-001",
    "a6_event_ids": ["A6-001", "A6-002"],
    "risk_basis": "...",
    "max_level": "HIGH",
    "level_distribution": {"HIGH": 1, "MEDIUM": 2},
    "status": "completed",
    "decision": "approve",
    "note": "by operator:zhang",
    "due_at": "...",
    "created_at": "...",
    "archived_at": "2026-08-13T19:30:00Z",
    "summary": "max_level=HIGH | decision=approve | by=operator:zhang | aggregated 2 events"
  },
  "P8J-20260813-190000-002": { ... }
}
```

#### 5.1.4 为什么是仓库级（不是按 job_id 分文件）

- 长期记忆是"跨 job 共享的只读历史"（`recall_jobs` 查询时不限于某个 job_id）
- 一个 P8_job 归档后通过 `p8_job_id` 直接定位，无需扫描子目录
- 主流程作业数据 `data/jobs/{job_id}/` 是一次性的，过 90 天审计期后可能要清理；而 `_long_term/` 是永久归档

### 5.2 `A7/storage/p8_long_term.py`

**职责**：长期记忆持久化（JSON 文件）+ 函数式 API（不抽象、不预留）。
**与 P2/P4 区别**：P2/P4 用内存 `_MOCK_TASKS`（dict 进程级），P8 用磁盘 JSON 文件（仓库级共享）。

**关键代码**：

```python
"""P8 长期记忆：JSON 文件持久化（双层结构）。

存储结构（data/jobs/_long_term/）：
    p8_archive.index.json    索引层：p8_job_id → 一句话描述（轻量；LLM 每次 invoke 看）
    p8_archive.json          数据层：p8_job_id → 完整 archived P8Job（按需精确加载）

并发策略：threading.Lock（单进程多线程内互斥）。
跨进程场景本期不考虑（演示用不到）。
"""
import json
import logging
import os
import threading
from pathlib import Path

logger = logging.getLogger(__name__)

# === 路径常量（仓库根 → data/jobs/_long_term/）==========================
# __file__ = <root>/A7/storage/p8_long_term.py
_PROJECT_ROOT = Path(__file__).resolve().parent.parent.parent
LONG_TERM_DIR = _PROJECT_ROOT / "data" / "jobs" / "_long_term"
INDEX_FILE = LONG_TERM_DIR / "p8_archive.index.json"   # 索引层
ARCHIVE_FILE = LONG_TERM_DIR / "p8_archive.json"       # 数据层

# === 并发锁（单进程多线程内互斥）========================================
_lock = threading.Lock()

# === 运行时内存缓存（启动时加载；每次 save 后落盘）======================
# 索引层：p8_job_id → 一句话描述（str；约 80 字）
_index: dict[str, str] = {}
# 数据层：p8_job_id → 完整 archived P8Job dict
_archive: dict[str, dict] = {}


# === 通用 IO 工具（索引层 + 数据层共用）================================

def _load_json(path: Path) -> dict:
    """从磁盘加载 JSON（不存在 / 损坏 → 空 dict；不删除原文件）。"""
    if not path.exists():
        return {}
    try:
        with path.open("r", encoding="utf-8") as f:
            data = json.load(f)
        return data if isinstance(data, dict) else {}
    except (json.JSONDecodeError, OSError) as exc:
        logger.warning("[p8-long-term] load %s failed: %s; starting empty", path.name, exc)
        return {}


def _flush_json(path: Path, data: dict) -> None:
    """把 dict dump 到磁盘（tmp + 原子替换）。"""
    LONG_TERM_DIR.mkdir(parents=True, exist_ok=True)
    tmp = path.with_suffix(path.suffix + ".tmp")
    with tmp.open("w", encoding="utf-8") as f:
        json.dump(data, f, ensure_ascii=False, indent=2)
    # 原子替换（避免写到一半进程挂掉留下破损文件）
    os.replace(tmp, path)


# === 索引条目构造（依赖 A7/summary/p8_job_summarizer）=================

def _make_index_entry(archived_job: dict) -> str:
    """从 archived_job 构造索引条目（一句话描述）。

    格式模板：
        [<max_level>] <risk_basis 前 30 字>；<decision> by <decider> @ <archived_at 截 YYYY-MM-DD HH:MM>

    Args:
        archived_job: 已归档的 P8Job dict（含 max_level / risk_basis / decision / note / archived_at）

    Returns:
        一句话描述字符串
    """
    from A7.summary.p8_job_summarizer import summarize_p8_job  # 延迟 import 避免循环依赖

    level = archived_job.get("max_level", "N/A")
    basis = archived_job.get("risk_basis", "")[:30]
    decision = archived_job.get("decision") or "N/A"
    # 从 note 字段提取决策者（约定格式："by {user_id}"）
    note = archived_job.get("note", "")
    decider = note.split("by ", 1)[-1].strip() if "by " in note else "system"
    # 截短时间戳到分钟
    archived_at = archived_job.get("archived_at", "")
    ts_short = archived_at[:16] if archived_at else "N/A"  # ISO8601 前 16 字符 = YYYY-MM-DDTHH:MM

    return f"[{level}] {basis}；{decision} by {decider} @ {ts_short}"


# === 模块初始化（进程启动时加载一次）====================================

def _init() -> None:
    global _index, _archive
    _index = _load_json(INDEX_FILE)
    _archive = _load_json(ARCHIVE_FILE)


_init()


# === 公开 API ============================================================

def save_archived_job(p8_job_id: str, archived_job: dict) -> bool:
    """保存归档 P8_job（覆盖式）；同时更新索引层；写后立即落盘。

    Args:
        p8_job_id: P8_job ID
        archived_job: 归档 dict（含 summary / archived_at 等附加字段）

    Returns:
        True 成功；False 失败

    Side effects:
        - 更新 _archive[p8_job_id]（数据层）
        - 更新 _index[p8_job_id]（索引层；自动生成一句话描述）
        - 写两个文件到磁盘
    """
    try:
        with _lock:
            _archive[p8_job_id] = archived_job
            _index[p8_job_id] = _make_index_entry(archived_job)
            _flush_json(ARCHIVE_FILE, _archive)
            _flush_json(INDEX_FILE, _index)
        return True
    except OSError as exc:
        logger.exception("[p8-long-term] save failed for %s: %s", p8_job_id, exc)
        return False


def get_archived_job(p8_job_id: str) -> dict | None:
    """按 p8_job_id 查询已归档 P8_job（数据层；按需精确加载）。"""
    with _lock:
        return _archive.get(p8_job_id)


def get_index_entry(p8_job_id: str) -> str | None:
    """按 p8_job_id 查询索引条目（一句话描述；轻量）。"""
    with _lock:
        return _index.get(p8_job_id)


def search_archived_jobs(query: str, limit: int = 20) -> list[dict]:
    """子串搜索（数据层）：query 命中 risk_basis / note / a6_event_ids 任一字段。

    Args:
        query: 搜索关键词（不区分大小写）
        limit: 返回结果数上限

    Returns:
        命中的归档列表（完整 dict；非索引）

    Note:
        如需节省 token，请用 search_archived_descriptions()（仅返回索引）。
    """
    q = query.lower()
    with _lock:
        results = []
        for job in _archive.values():
            searchable = " ".join([
                job.get("risk_basis", ""),
                job.get("note", ""),
                " ".join(job.get("a6_event_ids", [])),
                job.get("p8_job_id", ""),
            ]).lower()
            if q in searchable:
                results.append(job)
                if len(results) >= limit:
                    break
        return results


def search_archived_descriptions(query: str, limit: int = 20) -> list[tuple[str, str]]:
    """子串搜索（索引层）：query 命中一句话描述。

    LLM 检索长期记忆的**首选入口** — 先返回轻量的 (p8_job_id, 描述) 列表，
    LLM 据此决定是否精确查询（get_archived_job）。

    Args:
        query: 搜索关键词（不区分大小写）
        limit: 返回结果数上限

    Returns:
        [(p8_job_id, 一句话描述), ...]
    """
    q = query.lower()
    with _lock:
        results = []
        for p8_job_id, desc in _index.items():
            if q in desc.lower():
                results.append((p8_job_id, desc))
                if len(results) >= limit:
                    break
        return results


def load_all_archived_jobs() -> list[dict]:
    """返回所有已归档 P8_job 列表（数据层 snapshot）。"""
    with _lock:
        return list(_archive.values())


def load_all_index_entries() -> list[tuple[str, str]]:
    """返回所有索引条目列表（索引层 snapshot）。

    Returns:
        [(p8_job_id, 一句话描述), ...]
    """
    with _lock:
        return list(_index.items())


def reset_archive() -> None:
    """清空归档（仅清内存 + 删磁盘文件）；测试用。

    同时清空索引层 + 数据层两个文件。
    """
    global _archive, _index
    with _lock:
        _archive.clear()
        _index.clear()
        if ARCHIVE_FILE.exists():
            ARCHIVE_FILE.unlink()
        if INDEX_FILE.exists():
            INDEX_FILE.unlink()
```

### 5.3 失败语义

| 失败场景 | 处理 |
|---------|------|
| 磁盘文件不存在 | 视为空 dict，不抛异常（首次运行正常） |
| 文件 JSON 损坏 | 警告日志 + 返回空 dict（**不删除原文件**；防止误覆盖可恢复数据） |
| 写文件失败（磁盘满 / 权限） | 返回 False + 异常日志（**不抛**便于 CLI / 前端调用；如需排查查日志） |
| 进程重启 | 自动从磁盘加载到内存（`_init()` 在 import 时执行；索引层 + 数据层分别加载） |
| 多进程并发写 | 本期**不考虑**；触发条件是"多 worker 同时归档"（未来升级到 SQLite 时解决） |
| 索引层与数据层不同步（如手工编辑） | `get_archived_job()` 优先信任数据层；`get_index_entry()` 可能返回过期描述（可接受，描述用于 LLM 决策） |

### 5.4 双层结构的 LLM 使用模式

LLM 调 `recall_jobs(query)` 时应**两步走**（详见主设计文档 § 5.3 业务规则第 8 条）：

```
Step 1: 索引层扫描（轻量）
    ↓
LLM 调 search_archived_descriptions(query)
    ↓
返回 [(p8_job_id, 一句话描述), ...]  ← LLM 看到这些描述
    ↓
LLM 判断：哪些相关？是否需要详情？
    ↓
Step 2: 数据层精确加载（按需）
    ↓
LLM 调 get_archived_job(p8_job_id)  ← 仅对感兴趣的 ID
    ↓
返回完整 archived P8Job dict
```

**禁止做法**：把全部长期记忆一次性塞给 LLM（费 token + 决策干扰）。

#### 7.1.1 调用流程

```
P8_agent.notify_feishu(p8_job_id, message)        ← 未来工具
        │
        ▼
A7/notify.send_feishu(p8_job, job_id)
        │
        ├─→ _build_push_message()           拼装 PushMessage（按 N=1 / N>1 选模板）
        ├─→ resolve_recipients(role)        从 FEISHU_USER_MAP 过滤 role → 收件人列表
        │                                    （0 个 → 降级 status="failed"；不抛异常）
        ├─→ _send_to_recipient() ×N         每个收件人：agents.channel_gateway_client
        │   .send_message(...)                  send_message(text=body, conversation_id=...,
        │                                       receive_id_type=chat_id|open_id,
        │                                       idempotency_key=p8_job_id, metadata=...)
        │
        └─→ FeishuNotifyResult              ok / partial / failed（绝不抛异常；§ 8.3）
```

#### 7.1.2 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 不直接调飞书 HTTP | 走 `agents/channel_gateway_client.send_message()` | 避免双客户端、双配置、双重重试；channel_gateway_client 已封装完整 HTTP + 认证 + 幂等 |
| idempotency_key | 固定 = `p8_job.p8_job_id` | 网关对相同 key 返回 cached receipt；同一 P8_job 重发 / 并发 / 重启都不会产生重复消息 |
| 失败降级 | 网关 GatewayError / 网络异常 → 该 recipient.status="failed"；聚合 status="partial"/"failed"；**不抛异常** | § 8.3：飞书推送失败不阻塞 P8_job 推进；LLM 看到失败可决定是否重试 |
| 收件人数据模型 | `FEISHU_USER_MAP = {open_id: {role, name}}`（2026-08-13 重构 / 2026-08-17 清理 chat_id） | open_id 是飞书用户唯一 ID；同一 role 可对应多人 → 群发；name 是中文姓名便于审计 |
| receive_id_type 固定 | 统一为 `"open_id"`（单聊）单聊 | 群发走 `FEISHU_GROUP_MAP` + `send_to_group(group_name=...)`，USER_MAP 不再承担群维度 |
| metadata 透传 | `{p8_job_id, job_id, risk_level, assignee_role, channel_decision: "PUSH", a6_event_count, recipient_count, recipient_open_id, recipient_name}` | 网关层可审计；运维侧排查不必进 P8 数据库 |
| `channel` 固定 | 写死 `"feishu"`（适配器名） | 本模块是飞书专用；多通道扩展可派生 `p8_lark_adapter` |

#### 7.1.5 与其他模块的关系

#### 7.3.3 .env 写入策略（不破坏既有内容）

1. `parse_env_file()` 把 .env 解析为 `[(key, value, comment_lines)]` 列表，
   保留 **注释 + 空行 + key 顺序 + 其他无关 key（OPENAI_API_KEY 等）**。
2. 受管 key 做 **in-place 更新**；新 key 追加到末尾（带 section header 注释）。
3. `FEISHU_USER_MAP` 解析为 dict → 用户编辑 → 重新序列化写回。
4. 写前自动备份 `.env.bak`（`shutil.copy2`）。
5. `tmp + os.replace` 原子替换（中断不会留半截文件）。
6. **自动清理**：保存时如发现旧 `FEISHU_CONVERSATION_MAP` / `FEISHU_GROUP_<ROLE>` 残留，一并删除（UI ③ 区显示警告）。

#### 7.3.4 敏感字段处理规则

| 用户输入 | 行为 |

| `"***"` | **保留原值**（不写盘；从已有 .env 读回原值） |
| `""`（空字符串） | **删除该 key** |
| 任何其他值 | **覆盖**为新值 |

涵盖 `CG_API_KEY` / `CHANNEL_GATEWAY_API_KEY` / `FEISHU_APP_SECRET`。

### 7.4 实时监听 chat_id / open_id 捕获（`feishu_config_app.py` 内部子模块）

**职责**：让用户在 UI 上**一键捕获**飞书群/单聊的 `chat_id` / `open_id`，
避免手工翻 `gateway-state.json` 或调用 Open API 查询。

#### 7.4.1 设计动机

运维痛点：要让 `FEISHU_USER_MAP` 真正可用，必须填入真实的 `oc_xxx` /
`ou_xxx`，但这些 ID 在飞书后台**没有"复制"按钮**，必须：

| 旧方式 | 痛点 |
|--------|------|
| 翻 `gateway-state.json` | 需要先发消息触发 webhook；JSON 嵌套深；新手找不到 |
| 调飞书 Open API `GET /im/v1/chats` | 需要 `chat:list` 权限，配置繁琐 |
| 让群成员手动告知 | 不现实 |

新方式：**点 ⑤ 区 ▶ 开始监听 → 群里发条消息 → 表格里点选 → 填 role + name → 保存**。

#### 7.4.2 工作流程

#### 7.4.3 API 列表

| 路由 | 方法 | 前置条件 | 职责 |
|------|------|---------|------|
| `/api/feishu/listener/start` | POST | ① + ② 已配 | 创建后台线程，开始轮询 `/v1/events` |
| `/api/feishu/listener/status` | GET | 无 | 返回当前活跃 listener 的 snapshot（含 events 列表） |
| `/api/feishu/listener/stop` | POST | 无 | 停止当前活跃 listener |
| `/api/feishu/listener/save` | POST | 已选事件 + role + name | 把选中事件的 chat_id/open_id 写入 FEISHU_USER_MAP |

#### 7.4.4 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 轮询 vs SSE | **轮询 2s** | Gateway 暂不推 SSE；2s 是平衡延迟与负载的折中 |
| 守护线程 | `daemon=True` | 进程退出自动结束；不阻塞 Flask shutdown |
| 单实例 | 最多同时 1 个活跃 listener | 新 start 自动 stop 旧的；避免重复轮询浪费 Gateway 资源 |
| 缓冲限长 | 最多 50 条事件 | 防止长时间监听内存膨胀 |
| 前置检查 | start 前校验 GATEWAY_HOST + CG_API_KEY | 没配就启动 = 永远 401，没意义；早失败 |
| 写入方式 | 统一写入 `FEISHU_USER_MAP`（按 open_id 主键） | open_id 是飞书用户唯一 ID；新数据模型的唯一合法入口 |
| 自动选 ID 类型 | 按 `conversation.type` 预选 channel | `group` → chat_id；`direct` → open_id；减少误操作 |

#### 7.4.5 关键函数

| 函数 | 职责 |
|------|------|
| `GatewayListener._poll_once()` | 单次 GET `/v1/events?after_sequence=N`；归一化事件；追加到缓冲 |
| `GatewayListener._normalize_event()` | 把 Gateway 原始事件 → UI 友好结构（取 `sender.id` / `conversation.id`） |
| `api_delete_config_item(type, key)` (`POST /api/feishu/config/delete`) | 按主键删除 USER_MAP 或 GROUP_MAP 单条配置（前端点删除 → `confirm()` → 立即写盘） |
| `get_active_listener()` | 返回当前唯一活跃 listener（线程安全） |
| `stop_all_listeners(reason)` | 进程退出时统一清理 |

#### 7.4.6 与现有模块的关系

| 模块 | 关系 |
|------|------|
| `agents/channel_gateway_client.py` | 监听调用同一个 Gateway 的 `/v1/events` 端点（不冲突，GET-only） |
| `A7/notify/feishu_sender.py` | 监听产出的 open_id/chat_id 直接被它消费（运行时 USER_MAP 解析） |

### 7.5 `A7/notify/feishu_receiver.py`（飞书通道适配：精简收件端，2026-08-17 重构）

**职责**：从 Channel Gateway 拉取入站事件，是 `feishu_sender.py`（发送端）的对偶模块。

**与 `feishu_sender` 的关系**：

| 维度 | `feishu_sender.py` | `feishu_receiver.py` |
|------|---------------------|----------------------|
| 方向 | 主动发消息（Agent → 飞书） | 拉入站事件（飞书 → Agent） |
| HTTP | `POST /v1/messages/send` | `GET /v1/events` |
| 关注 | 幂等键 / 聚合模板 / 收件人解析 | 过滤 / 序列管理 / ACK |

#### 7.5.1 公开 API

| 函数 | 签名 | 职责 |
|------|------|------|
| `format_event(event, *, user_map, group_map)` | `-> str` | 把一条事件格式化为可读单行字符串：`<时间>  <人名> (<单聊\|群聊:群名>) \| <消息内容>` |
| `poll_once(*, initial_sequence, account_id, group_name, person_name, channel)` | `-> List[dict]` | 单次拉取匹配过滤条件的事件，返回事件列表（无事件返回 `[]`） |
| `poll_and_print(*, ..., account_id, group_name, person_name, ...)` | `-> int` | 持续轮询并打印，每条事件打印 `有新消息啦`（+ 可选 JSON） |
| `mark_event_status(event_id, *, status, details)` | `-> dict` | 主动修改一条事件状态（封装 `/v1/events/{id}/ack`） |

#### 7.5.2 过滤参数（client-side）

| 参数 | 过滤规则 |
|------|---------|
| `account_id` | 按 `event.accountId` 精确匹配（gateway `/v1/events` 不直接支持，client-side 实现） |
| `group_name + person_name` | 群聊过滤：要求 `conversation.type` 是群 + `GROUP_MAP[chat_id].name == group_name` + `USER_MAP[open_id].name == person_name` |
| `person_name`（alone） | 单聊过滤：要求 `conversation.type` 是单聊 + `USER_MAP[open_id].name == person_name` |
| 都不传 | 全部放行 |

`--group-name` 必须与 `--person-name` 一起使用（互斥校验）；单独 `--person-name` 为单聊过滤。

#### 7.5.3 CLI（`python -m A7.notify.feishu_receiver`）

```bash
# 默认：持续轮询，每条新事件打印 "有新消息啦"（Ctrl+C 停止）
python -m A7.notify.feishu_receiver poll

# 单次拉取：无新消息返回空；有新消息打印 "有新消息啦" + 完整 event JSON
python -m A7.notify.feishu_receiver poll --once

# 显式重放历史（从 sequence=0 开始拉所有事件）
python -m A7.notify.feishu_receiver poll --initial-sequence 0 --once --exit-after 5

# 按 account_id 过滤
python -m A7.notify.feishu_receiver poll --account-id default --once

# 群聊过滤（群名 + 人名）
python -m A7.notify.feishu_receiver poll --once --group-name "应急响应群" --person-name "张三"

# 单聊过滤（人名 alone）
python -m A7.notify.feishu_receiver poll --once --person-name "李四"

# 主动 ACK / ignore 一条事件
python -m A7.notify.feishu_receiver mark --event-id evt_xxx --status acked
```

`--once` 模式输出示例：

```
$ python -m A7.notify.feishu_receiver poll --once --person-name "张三"
有新消息啦
[
  {
    "platformEventId": "546edf1d8e5c0f477a5eb581049dc785",
    "channel": "feishu",
    "accountId": "default",
    ...
  }
]
```

#### 7.5.4 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 打印格式 | 默认 `"有新消息啦"` 单行 | 简洁通知；完整数据走 return（poll_once）或 `--show-raw` |
| account_id 过滤 | client-side | gateway `/v1/events` 不直接支持 account_id 参数；client-side 按 `event.accountId` 字段过滤简单可靠 |
| 群聊 / 单聊过滤 | client-side 基于 USER_MAP / GROUP_MAP | gateway 不解析业务语义；反查 .env 配置在 client 端做 |
| `poll_once` vs `poll_and_print` 拆分 | 单次 vs 持续 | 单次模式返回完整 JSON 便于脚本串行；持续模式封装循环 + sleep |
| 序列管理 | 本批事件最大 sequence 作为下次起点 | 不依赖 gateway `latestSequence` 字段（命名不一致） |
| 自动跳过历史 | `--initial-sequence -1` | 先拉一批 events 取最大 sequence，避免重放历史 |

```json
      {"tag": "markdown", "content": "【告警】可燃气体浓度异常"},
      {"tag": "action", "actions": [
        {"tag": "button", "text": {"tag": "plain_text", "content": "已知悉"},
         "type": "default", "value": "{\"action\":\"ack\",\"alert_id\":\"gas_20260817_001\"}"},
        {"tag": "button", "text": {"tag": "plain_text", "content": "立即处理"},
         "type": "primary", "value": "{\"action\":\"handle\",\"alert_id\":\"gas_20260817_001\"}"},
        {"tag": "button", "text": {"tag": "plain_text", "content": "误报"},
         "type": "danger", "value": "{\"action\":\"false_alarm\",\"alert_id\":\"gas_20260817_001\"}"}
      ]}
    ]
  }
}
```

**V5 与 V4 的核心差异**：

| 字段 | V4（Card 1.0） | V5（Card 2.0） |
|------|----------------|----------------|
| 顶层 schema | 无 | `"schema": "2.0"`（强制） |
| 元素位置 | `elements`（平铺） | `body.elements`（嵌套） |
| 文本块 | `{"tag":"div","text":{"tag":"lark_md","content":...}}` | `{"tag":"markdown","content":"..."}` |
| 按钮 `value` | `dict`（{"action":..., "alert_id":...}） | **`string`**（必须 JSON 字符串化） |
| value 格式 | 默认带空格 | **紧凑 `separators=(",",":")`**（与 cardkit 一致） |

> 注：Card 1.0 → 2.0 不是可选项。cardkit `PUT /open-apis/cardkit/v1/cards/{id}` 校验 `schema` 必须为 `"2.0"`，否则返回错误码 300303「Only schema 2.0 is supported」。

#### 7.6.7 cardkit 发送链路（V5 — 2026-08-18 重写）

`send_to_group_card` 严格按 [`docs/飞书卡片教程/`](飞书卡片教程/) 的官方 cardkit 路径，分三步：

```
build_feishu_card(text, options, title, alert_id)  ← 仅产 Card 2.0 dict（不调网络）
       │
       ▼
send_to_group_card(card, *, chat_id/group_name, account_id, alert_id)
       │
       ├─ Step 1: feishu_card.create_card_entity(card)          ← 业务端直调飞书
       │          POST /open-apis/cardkit/v1/cards/            （不走 Gateway）
       │          body = {card:{type:"card_json", data:"<JSON stringified>"}, uuid}
       │          → 拿 card_id
       │
       ├─ Step 2: send_message(text="", msg_type="interactive",
       │                       content=json.dumps({"card_id": card_id}))
       │          → Gateway → im/v1/messages
       │          （Gateway 只需透传 msg_type + content，无需解析 card 内容）
       │
       └─ Step 3: register_card(alert_id, card_id, account_id, message_id)
                  → 写 data/feishu_card_index.json（持久化）
                  → 供 callback 时反查，按 alert_id 拿 card_id 异步更新卡片
```

**为什么不再需要 Gateway 解析 card JSON**：
- V4 时代业务端把完整 Card JSON 塞进 `content`，Gateway `feishu.js` 需要拆开 `card.elements[0].text.content` 取 `text` 兜底字段（因为 Gateway `POST /v1/messages/send` 校验 `text` 非空）。
- V5 改为两步：业务端**先**调 cardkit 拿 `card_id`；**再**用 `content={"card_id":"..."}` 发 im/v1/messages。此时 Gateway `text` 字段直接传空字符串，Gateway 校验时只要 `text` 为字符串（可空）即可通过，无需解析 Card JSON。
- Gateway `feishu.js` 改动面更小：只需透传 `msg_type` + `content`，**不**需要读 Card 内部结构。

**为什么业务端可以直接调 cardkit**：cardkit 是飞书 OpenAPI（与 im/v1/messages 同级），不是 Gateway 内部接口。业务端直调是官方支持的常规路径；tenant_access_token 按 `(app_id, domain)` 进程内缓存（[`A7/notify/feishu_card.py`](../A7/notify/feishu_card.py) 段 2）。

**send_to_group_card 异常处理**：

| 失败点 | 行为 |
|--------|------|
| Step 1 cardkit 创建失败（鉴权/网络/schema 不合法） | `FeishuCardkitError` 抛出 → CLI 退出码 1；消息不会发出 |
| Step 2 im/v1/messages 失败（Gateway 业务错误） | `GatewayError` 抛出 → CLI 退出码 1；**card_id 已创建但消息未发**，下次重试会因相同 `idempotency_key` 命中 Gateway 端幂等 |
| Step 3 register_card 落盘失败 | 写 logger.exception；不抛出（消息已成功发出；callback 时找不到 card_id 跳过异步更新，但 toast 已返） |

#### 7.6.5 底层依赖：`agents.channel_gateway_client.send_message` 扩展

为了支持 Card，`channel_gateway_client.ChannelGatewayClient.send_message` 与模块级 `send_message` 都新增两个参数：


#### 7.6.6 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| Card 模式开关 | CLI `--card` flag | 默认纯文本，零侵入；运维按需启用 |
| 选项入参格式 | `LABEL:ACTION` 字符串 + `action="append"` | 与既有 CLI 风格一致；多个选项无需多 flag |
| 按钮 value 字段 | `{"action": ..., "alert_id": ...}` | action 用于业务分发；alert_id 用于回调时匹配原卡片 |
| alert_id 可选 | 仅当显式传入时写入 value | 避免空值污染回调数据；运维可省略 |
| ensure_ascii=False | `json.dumps(card, ensure_ascii=False)` | 标题/正文含中文时不转义；飞书 API 接受 UTF-8 |
| 标题为空 | 回退到 `DEFAULT_CARD_TITLE="告警通知"` | 与 Python falsy 语义一致；UI 友好 |
| 全空白 option 字符串 | 静默跳过 | CLI 用户偶尔会粘贴带空白的字符串，不应阻断整个发送 |
| Gateway `code != 0` | 视为发送失败，抛 `GatewayError` | 与现有 `send_to_group` 错误处理一致 |

#### 7.7.2 url_verification 握手 bug 修复（2026-08-17）

原 `FeishuAdapter.receive()` 在 `verifyToken()` **之后**才检查 `url_verification`：

```javascript
// 错误顺序（修复前）：
const isChallenge = payload?.type === "url_verification";
this.verifyToken(payload, accountConfig);   // ← url_verification 没有 token → 401
if (isChallenge) return { response: { challenge } };   // 永远走不到
```

飞书的 url_verification payload 是 `{"challenge":"xxx","type":"url_verification"}`，**没有 token 字段**。`verifyToken` 拿 `payload?.header?.token ?? payload?.token`（undefined）跟 `verificationToken` 做 `constantTimeEqual`，永远不等 → Gateway 返回 401 → 飞书标记「目标回调服务器未在线」。

**修复**：把 `isChallenge` 检查移到 `verifyToken` **之前**，url_verification 直接走 challenge 响应：

```javascript
// 正确顺序（修复后）：
const isChallenge = payload?.type === "url_verification";
if (isChallenge) return { response: { challenge } };  // 直接返回，不校验 token
this.verifyToken(payload, accountConfig);   // 只对普通事件校验
```

#### 7.7.5 V5 行为：Card 2.0 + 异步 cardkit 更新（2026-08-18 重构）

V5 严格按 [`docs/飞书卡片教程/`](飞书卡片教程/) 的官方路径：**callback 响应里不再返回 `card` 字段**，改为同步返回 `{toast}` + **daemon 线程异步**调 `PUT /open-apis/cardkit/v1/cards/{card_id}` 全量更新卡片。

##### 为什么去掉 callback 响应里的 `card` 字段

V3/V4 的"实时替换"做法（返回 `{toast, card: {type:"card", data:{card:...}}}`）触发了用户报告的两个生产 bug：

1. **不稳定**：飞书客户端把 callback 返回的 `card` 当成"实时替换"——这不是飞书开放平台文档保证的行为，部分飞书版本会报"显示出错"。
2. **不可更新**：飞书官方文档明确说明在交互期间（错误码 200810）**不能流式更新**。返回 `card` 强行覆盖在某些场景会失败（错误码：`The card is in an ongoing interaction and cannot be updated`）。

V5 的修正：
- callback 响应**只返回 toast**（飞书 callback 协议唯一支持的实时反馈形式）
- 卡片替换走**业务端后续调 PUT cardkit**（教程：[`docs/飞书卡片教程/全量更新卡片.md`](飞书卡片教程/全量更新卡片.md)）
- `sequence` 严格递增（持久化在 `data/feishu_card_index.json`，每次成功更新 +1）

##### 7.7.5.1 幂等检查

同一 `alert_id` **只能被处理一次**。第二次点击同一 alert_id：
- 不写审计日志
- 不再异步更新卡片（避免 sequence 错乱）
- 给点击者返回 `toast: warning`，提示「已被 XXX 于 HH:MM 处置（YYY）」

实现：`_check_already_processed()` 在写日志前扫 audit log 倒序找最早匹配。

##### 7.7.5.2 异步更新卡片（daemon 线程 fire-and-forget）

首次点击后，业务端返回 `{"toast":{"type":"success"}}`（**不返回 card 字段**），同时启动 daemon 线程异步调 `PUT cardkit` 全量更新卡片。

```python
# _build_processed_card() 生成的「已处置」卡 JSON（Card 2.0 schema）
{
  "schema": "2.0",
  "header": {
    "template": "green",  # 颜色：green=已处置 / red=告警 / grey=已关闭
    "title": {"tag": "plain_text", "content": "已处置 · 立即处理"}
  },
  "body": {
    "elements": [
      {"tag": "markdown", "content":
        "**告警 ID**：`gas_20260817_001`\n"
        "**处理结果**：立即处理\n"
        "**处理人**：李宗睿\n"
        "**处理时间**：2026-08-17T17:54:17"
      },
      {"tag": "hr"},
      {"tag": "markdown", "content":
        "✅ 本告警已处置完毕，群内卡片已锁定。"
        "如需重新发起处置，请联系值班管理员。"
      }
    ]
  }
}

# 回给飞书的响应体（仅 toast，无 card）
{
  "toast": {
    "type": "success",
    "content": "已记录您的处置（立即处理）"
  }
}

# 异步调用（daemon 线程；不影响已返回的 toast 响应）：
PUT /open-apis/cardkit/v1/cards/{card_id}
Authorization: Bearer <tenant_access_token>
Content-Type: application/json; charset=utf-8
{
  "card": {"type": "card_json", "data": "<stringified Card 2.0 JSON>"},
  "uuid": "<random>",
  "sequence": 1    # ← 严格递增（首次更新 = 1；持久化在 feishu_card_index.json）
}
```

**sequence 管理**：
- 第一次更新：`sequence=1`（读 index 时 `existing.sequence=0` → +1）
- 第二次更新：`sequence=2`（读 index 时 `existing.sequence=1` → +1）
- 每次成功 PUT 后 `register_card(alert_id, card_id, sequence=new_seq)` 把新值写回 index
- 飞书要求严格递增（错误码 300317「The sequence number for operating on the card did not increment consecutively」）

**注意**：Card 替换是群内全局生效（飞书原生行为），不支持 per-user 状态。所有人看到的卡都一样。

##### 7.7.5.3 字段兜底

某些 Feishu Card 配置（特别是第三方模板或老版本飞书）不会带 `action.text.content` 或 `operator.user_name`，V2 加了兜底，V5 保留：

| 字段 | 缺失时来源 |
|------|-----------|
| `button_text` | `_ACTION_LABELS` 映射（`handle→立即处理`、`ack→已知悉`、`false_alarm→误报` 等） |
| `operator_name` | `.env` 的 `FEISHU_USER_MAP`（按 `open_id` 反查） |

实现：`_extract_action()` + `_lookup_user_name()` + `_action_label()`。

##### 7.7.5.4 业务编排下沉（2026-08-18 V3 新增 → V5 保留）

V3 把核心业务流程抽成一个**公开 API**：`process_card_callback(payload: dict) -> dict`，
让 [`A7/notify/feishu_card.py`](../A7/notify/feishu_card.py) 的 HTTP 入口
`handle_card_callback` 与 [`A7/notify/feishu_receiver.py`](../A7/notify/feishu_receiver.py)
的 `process_card_callback` re-export 共享同一份逻辑。V5 完整保留此设计。

**API 签名**：

```python
def process_card_callback(payload: dict) -> dict:
    """处理一个飞书 Card 按钮点击 payload，返回回给飞书的完整响应体。

    V5 行为：同步返回 toast；首次成功时异步 daemon 线程调 PUT cardkit 更新卡片。
    """
```

**返回字典的 5 种形态**（按顺序短路）：

| # | 触发条件 | 返回 |
|---|---------|------|
| 1 | `payload` 是 `None` / 非 dict / list（防御） | `{"status": "error", "error": "payload must be a JSON object"}` |
| 2 | `payload.type == "url_verification"` | `{"challenge": "..."}` |
| 3 | 入参非法（缺 `event.action.value.action`） | `{"status": "error", "error": "missing event.action.value.action"}` |
| 4 | 幂等命中（同 alert_id 已处置） | `{"toast": {"type": "warning", "content": "..."}}` |
| 5 | 首次成功 | `{"toast": {"type": "success", "content": "..."}}`（异步触发 PUT cardkit） |

**调用链**：

```
飞书服务器 → Gateway(/webhooks/feishu/P8)
         → 业务端 web/server.py → handle_card_callback(handler, data)
                                  │
                                  ├─ process_card_callback(data)  ← 核心业务逻辑
                                  │   ├─ url_verification / 入参校验 / 幂等
                                  │   ├─ _write_audit(record)        ← 仅首次成功
                                  │   ├─ _build_processed_card(...)  ← Card 2.0 替换卡
                                  │   └─ _update_card_async(...)     ← daemon 线程 fire-and-forget
                                  │       │
                                  │       └─ feishu_card.create_card_entity / update_card_entity
                                  │           └─ 直接调飞书 OpenAPI（不走 Gateway）
                                  │
                                  └─ handler.send_json(reply, status=200|400)

A7/notify/feishu_receiver.py
         └─ process_card_callback(payload)  ← 直接委托给 feishu_card 版本
         └─ format_card_callback(payload)   ← 可读单行格式化（调试 / CLI）
```

**关键收益（V5）**：

- **严格按官方路径**：飞书 callback 协议**只支持 toast**实时反馈；卡片替换必须由业务端后续调 PUT cardkit。V5 不再尝试实时返回 `card` 字段。
- **响应格式统一**：去掉 `_wrap_card()`（V3 引入的嵌套包装层）；callback 响应固定为 `{toast}`，飞书侧解析失败的可能性消失。
- **可复用**：`feishu_receiver` 现在能 import `process_card_callback`，未来 Gateway 若改造让 card 事件入流，receiver 就能直接处理。
- **可测试**：纯函数（除 `_write_audit` + daemon 线程外无副作用），便于单测覆盖 5 种返回形态。
- **HTTP 入口简化**：`handle_card_callback` 只负责日志 + 状态码分流，业务逻辑下沉到 `process_card_callback`。

#### 7.7.6 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| **入口：业务端 8080 vs Gateway 8787** | Gateway `/webhooks/feishu/P8`（Feishu 标准 webhook 入口） | 复用现有 8787 穿透 + 标准 webhook URL 模式；不引入独立的 `/api/feishu/card-callback` 旁路 |
| **是否鉴权** | Gateway token + signature | 普通事件校验 `header.token` 与 `verificationToken` 一致；url_verification 跳过 |
| **Card 事件走法** | Gateway 适配器同步代理到业务端（不是事件流异步分发） | 飞书要求 2s 内同步响应；事件流是异步的，不能满足 |
| **幂等粒度** | **per-alert_id**（任意 action 第二次点击都拦截） | 业务语义：一个告警只能有一种处置结果；最早点击者「获胜」 |
| **Card schema** | **强制 Card 2.0**（`schema: "2.0"`） | cardkit 更新接口仅支持 2.0（错误码 300303「Only schema 2.0 is supported」）；不升级无法走通 |
| **Card 替换时机（V5）** | **仅返回 toast**（不再返回 card 字段）+ daemon 线程异步调 PUT cardkit | 飞书 callback 协议**只支持 toast**实时反馈；交互期间（错误码 200810）禁止实时更新。V5 把更新放到 callback 之外的 PUT cardkit 异步执行 |
| **sequence 管理** | 持久化在 `data/feishu_card_index.json`，每次成功 PUT 后 +1 | cardkit 要求严格递增（错误码 300317）；持久化保证重启后能续号 |
| **持久化（card_index）** | `data/feishu_card_index.json` + `threading.Lock` + atomic write（`tmp → os.replace`） | callback 时按 alert_id 反查 card_id；与现有 audit log 同模式；无新依赖 |
| **tenant_access_token 缓存** | 按 `(app_id, domain)` 进程内缓存；剩余有效期 < 60s 时刷新 | 飞书 token 最大有效期 2 小时；缓存避免每次 cardkit 调用都重新拉 |
| **业务端直调 cardkit** | 不绕开 Gateway（Gateway 仅用于 im/v1/messages 透传） | cardkit 是飞书 OpenAPI，业务端可直调；不需要 Gateway 路由 |
| **审计文件路径** | `data/card_callbacks.jsonl` | 绝对路径；线程锁保证并发安全 |
| **响应时延** | 同步处理 + 立即返回 200（daemon 异步更新不阻塞） | 飞书要求 2s 内响应；先写日志再返回，卡片更新后续异步 |
| **payload 字段脱敏** | logger 只记 action + alert_id + operator_open_id + button_text，不记 user_name | 满足 CLAUDE.md「敏感信息脱敏」原则 |
| **错误响应** | 缺 event/action.value → `400 + {"error": "missing event.action.value.action"}` | 便于飞书侧调试；不抛 500 防止飞书重试风暴 |
| **业务端 proxy 失败** | Gateway 返回 `{"toast":{"type":"error","content":"服务暂时不可用"}}` | 业务端挂了也回 200，避免飞书重试风暴；前端用户能看到提示 |
| **幂等冲突响应** | `{"toast":{"type":"warning","content":"该告警已被 XXX 于 HH:MM 处置（YYY）"}}` | 不再触发异步更新；让群里其他人看到的就是「最早一次」的处置结果 |

```python
def summarize_p8_job(job: dict) -> str:
    """从 P8_job 字段自动汇总 summary（归档时写入长期记忆）。
    
    Args:
        job: 工作记忆中的 P8_job dict
    
    Returns:
        简短摘要字符串，如：
        "max_level=HIGH | decision=approve | by=frontend:zhang | aggregated 3 events"
    """
    parts = [
        f"max_level={job.get('max_level')}",
        f"decision={job.get('decision') or 'N/A'}",
        f"by={_extract_decider(job.get('note', ''))}",
    ]
    if job.get("a6_event_ids") and len(job["a6_event_ids"]) > 1:
        parts.append(f"aggregated {len(job['a6_event_ids'])} events")
    return " | ".join(parts)


def _extract_decider(note: str) -> str:
    """从 note 字段提取决策者（约定格式："by {user_id}"）。"""
    if "by " in note:
        return note.split("by ")[-1].strip()
    return "system"
```

## 14. 关键决策回顾

| 决策 | 选择 | 理由 |
|------|------|------|
| agents/ 下 P8 只 1 个文件 | `p8_disposition_agent.py` | 与 P1-P7 命名一致；核心逻辑高聚合 |
| 外围全部下沉 A7 | 5 个子目录（prompt / schema / storage / notify / api / summary） | 职责分离；避免 agents/ 臃肿 |
| A7 = P8 专属 | 不抽象过早 | 当前只有 P8 用；按需扩展 |

| 无后台守护进程 / 轮询 worker | 新数据进入 P8 的两个唯一入口：(1) main 调 `execute_p8(p7_data=...)`；(2) 用户明确要求（执行 `read_p7_events` tool） | 避免无谓复杂度；按需触发而非持续拉取 |
| 飞书适配器独立 | `A7/notify/feishu_sender.py` | 加 P8 语义（幂等键 / 聚合模板），不污染原 client |
| 飞书配置 UI 独立 | `A7/notify/feishu_config_app.py` + `templates/feishu_config.html` | 端口 5003；写项目根 .env；不嵌 web/server.py；不写 agent_config/.env |
| 实时监听 chat_id | `GatewayListener` (后台线程轮询 `/v1/events`) | 避免手工查 `gateway-state.json`；UI 一键捕获；自动按 conversation.type 选 chat_id/open_id |
| REST 控制器独立 | `A7/api/p8_working_memory_ctrl.py` | 路由在 web/，业务逻辑下沉 |
| 系统提示词留 agents/ | `agents/system_prompt/P8_SYSTEM_PROMPT.md` | 面向开发，与代码同位置便于对照 |
| 业务规则放 A7/prompt/ | `A7/prompt/p8_prompt.py`（默认常量）+ `overrides/P8_RULES.user.md`（运行时覆盖） | 面向业务，非破坏性修改 + 一键恢复 |
